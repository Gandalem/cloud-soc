# SSH 탐지 파이프라인 우선 보완

## 적용 범위

기존 `raw-logs-* → normalized-events → security-alerts` 경로의 조회 완전성, 실패 처리, 조직별 집계, 시간 재현성과 근거 추적을 보완했습니다. 정적 대시보드, 에이전트 설치기, 서버 보안 설정은 변경하지 않습니다. `soc-host-raw-linux-*`·`soc-host-raw-windows-*`를 SSH 파서로 연결하지도 않습니다.

## 실행 전에 확인할 변경

### 기존 인덱스 매핑 준비

신규 인덱스에는 `cloud_soc.provenance`가 포함됩니다. 기존 인덱스는 일반 실행 중 자동 변경하지 않습니다. 필드가 없으면 데이터 처리 전에 종료 코드 `1`로 중단하고 준비 명령을 안내합니다.

아래 명령은 실제 Elasticsearch에 접속하여 두 대상 인덱스에 **새 필드 매핑을 추가**합니다. 인덱스가 없으면 생성합니다. 기존 문서 삭제·재색인·갱신은 하지 않으며, 이미 호환되는 필드가 있으면 다시 변경하지 않습니다. 호환되지 않는 필드가 있으면 중단합니다. 두 인덱스 변경은 트랜잭션이 아니므로 한쪽만 성공했다면 원인을 해결하고 재실행합니다.

이 작업에서는 아래 명령을 실제 서버에 실행하지 않았습니다. `.env`가 의도한 개발 클러스터를 가리키는지 확인하고, 필요한 경우 스냅샷을 확보한 뒤 실행하세요.

```powershell
$env:PYTHONPATH = (Join-Path (Get-Location) "src")
.\.venv\Scripts\python.exe -m cloud_soc.main --prepare-lineage-mappings
$LASTEXITCODE
```

`cloud_soc.provenance`는 `object`, `enabled: false`입니다. 근거와 규칙 스냅샷을 `_source`에 보존하지만 검색·집계용 필드로 인덱싱하지 않습니다. 임의 규칙 값이 동적 매핑 충돌을 만드는 것을 방지합니다. 향후 조사 API는 이 객체를 문서 조회로 읽고, 검색이 필요한 필드는 별도 계약과 매핑을 추가해야 합니다.

### 실행과 종료 코드

```powershell
.\.venv\Scripts\python.exe -m cloud_soc.main
$LASTEXITCODE
```

| 코드 | 의미 |
| --- | --- |
| `0` | 배치 완료 또는 매핑 준비 완료 |
| `1` | 연결·권한·조회·매핑·저장 등 처리 실패 |
| `2` | 배치는 진행했으나 유효하지 않은 문서 발생, 또는 CLI 인자 오류 |
| `130` | 사용자가 Ctrl+C로 중단 |

정규화 성공, 기존 문서, 미지원 로그, 잘못된 원본/정규화 문서, 새 경보 수를 구분합니다. 잘못된 문서는 원래 인덱스에 남기고 인덱스명·문서 ID를 오류 로그에 남깁니다. 민감할 수 있는 원본 로그 본문은 오류 출력에 넣지 않습니다. 미지원 형식은 파싱 성공으로 표시하지 않습니다.

`--watch`는 잘못된 개별 문서가 있어도 `DEGRADED` 상태로 다음 배치를 계속 처리합니다. 연결 오류·시간 초과·HTTP 429/502/503/504만 배치 단위로 최대 2회 추가 재시도합니다. 대기 시간은 `interval`, `2 × interval`이며 각각 최대 60초입니다. 정상 배치 후 연속 실패 횟수를 초기화합니다. 3회 연속 실패하면 종료 코드 `1`로 끝납니다. ES 클라이언트 자체의 HTTP 재시도가 추가로 발생할 수 있습니다. 인증 오류, 부분 검색, 프로그래밍 오류는 무한 재시도하지 않습니다.

`Pipeline OK`는 입력된 배치 처리 결과이며 수집기가 정상 작동한다는 건강도 판정은 아닙니다. 아직 raw 인덱스가 없는 초기 환경에서는 0건으로 끝날 수 있습니다. 수집 지연·수집기 장애의 판단은 별도 상태 수집이 필요합니다.

## 데이터 처리 계약

### 전체 조회

- raw와 normalized를 각각 PIT 스냅샷으로 열고 `search_after`로 끝까지 읽습니다. 페이지 크기는 1,000건이며 전체 조회 상한이 아닙니다.
- 같은 스냅샷에서는 `_shard_doc`으로 페이지를 이동하고 최신 PIT ID를 사용합니다. 성공·실패 모두 PIT 정리를 시도합니다.
- 시간 초과, 실패 샤드, 조기 종료, 비정상 커서는 완료로 처리하지 않습니다. 인덱스 refresh의 실패 샤드도 검사합니다.
- 모든 페이지를 확보한 후 해당 단계의 처리를 시작합니다. 탐지는 이벤트 시간과 내용 해시로 정렬하므로 같은 시각의 이벤트도 입력 순서에 따라 경보 ID가 바뀌지 않습니다.

### 조직과 시간

- 규칙에 없어도 `organization.id`를 탐지 그룹에 포함합니다. 조직별 5건을 합쳐 임계치 10건으로 판단하지 않습니다.
- 새 원본의 조직 ID가 없으면 `oci-dev`로 자동 대체하지 않습니다. 기존 Filebeat 설정에는 `organization.id=oci-dev`가 명시되어 있습니다.
- 조직 필드는 **분류와 집계 범위**일 뿐 신뢰할 수 있는 테넌트 인증 수단이 아닙니다. 악의적인 수집기의 조직 위조, 접근 통제, RBAC는 해결하지 않습니다.
- 연도가 없는 syslog는 원본의 `event.created`, 없으면 원본 `@timestamp`를 기준으로 해석합니다. 기준 시각에는 시간대가 필수이며 실행 시각으로 대체하지 않습니다.
- 로그 시간대는 원본 `event.timezone`이 우선입니다. 없으면 `--source-timezone`을 사용하며 기본값 `UTC`는 기존 OCI Ubuntu 환경을 전제로 합니다. 한국 시간 로그에는 `--source-timezone=+09:00`을 사용합니다. 음수 오프셋도 `--source-timezone=-05:00`처럼 지정합니다.
- 현재 지원하는 시간대 표기는 `UTC`, `Z`, `±HH:MM`입니다. 지역 이름과 DST 자동 해석은 지원하지 않습니다. 시간대가 섞인 수집 환경은 이벤트마다 올바른 숫자 오프셋을 제공해야 합니다.
- 소스 시간대의 기준 연도와 인접 연도 중 기준 시각보다 최대 하루 미래까지의 가장 최근 유효 날짜를 선택합니다. 연도 추정 사실, 기준 필드·시각, 시간대 기본값 사용 여부를 근거 메타데이터에 남깁니다. 오래된 로그를 뒤늦게 수집하거나 장시간 시계 오차가 있으면 실제 연도를 확정할 수 없으므로 별도 타임스탬프 계약이 필요합니다.

### 근거와 재처리

- 새 정규화 문서에 원본 인덱스·문서 ID를 저장합니다.
- 새 경보에는 실제 탐지 창에 포함된 정규화 문서 참조, 가능한 원본 참조, 이벤트 해시, 규칙 전체 스냅샷·해시와 엔진 버전을 저장합니다. 해시는 내부 문서 참조 메타데이터를 포함한 정규화 이벤트의 정렬된 JSON을 기준으로 합니다.
- 과거 정규화 문서에 원본 참조가 없으면 새 경보의 근거 상태를 `incomplete_legacy`로 표시합니다. `complete`는 참조 필드가 모두 있다는 뜻이지 원본이 지금도 존재한다는 검증 결과가 아닙니다.
- 같은 ID의 정규화 문서와 경보는 `create` 요청의 충돌을 확인하고 기존 문서를 유지합니다. 예전 오류 시각이나 누락된 근거를 자동 보정하지 않습니다. 보정은 별도 검증과 마이그레이션이 필요합니다.
- 새 경보 ID는 규칙 버전과 정확한 근거 목록도 포함합니다. 규칙·근거가 바뀌면 별도 경보로 남으며, 기존 버전에서 만든 경보를 삭제하지 않습니다. 따라서 최초 적용 시 같은 사건의 이전 경보와 새 경보가 함께 보일 수 있습니다.
- 이것은 애플리케이션의 덮어쓰기 방지이며 ES 관리자에 대한 변조 방지나 WORM 보관 기능이 아닙니다. 보존 기간이 지난 원본은 조회할 수 없으므로 근거 보존 정책이 필요합니다.

## 오프라인 검증

저장소 루트에서 실행합니다. 테스트는 가짜 Elasticsearch와 Mock을 사용하며 실제 인덱스에 접속하거나 에이전트를 설치하지 않습니다.

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -v
node --test --test-reporter=spec prototype/tests/logs.test.cjs deploy/agents/tests/installers.test.cjs
```

주요 회귀 사례는 10,010건 전체 조회, 첫 10,000건 뒤의 실패 탐지, 페이지 경계의 탐지 창, 조직 혼합 방지, 연도 경계·윤년·잘못된 날짜, 부분 검색·refresh, 저장 실패, 경보 근거 연결, 전체 파이프라인 재실행, 종료 코드와 재시도입니다.

실제 ES 9.5.2에서의 PIT·권한·매핑 적용·서비스 재시작 검증은 별도 통합 테스트가 필요합니다. 이번 테스트 통과만으로 운영 배포가 완료되지는 않습니다.

## 다음 우선순위

1. 영속 체크포인트, 지연 도착 허용 범위, 탐지 창·cooldown 상태 복구를 설계합니다. 현재는 매번 전체 데이터를 메모리에 읽고 기존 문서의 create 충돌도 다시 확인하므로 장기간 수집 환경에 적합하지 않습니다.
2. 반복 오류의 영속 격리와 상태 API를 추가합니다. 현재 오류는 로그와 카운터로만 보고하며 별도 dead-letter 저장소나 수집기 상태판은 없습니다.
3. 별도 개발 인덱스로 실제 ES 통합 테스트를 수행하고, 기존 데이터 보정이 필요하면 소급 처리 계획을 먼저 검토합니다. 운영 인덱스 삭제로 문제를 해결하지 않습니다.
4. 원격 수신의 TLS·인증·최소 권한·조직 신뢰 경계를 별도 구성한 후 OS별 파서 계약과 클라우드 감사 로그 한 종류를 단계적으로 연결합니다. 정적 화면의 실데이터 API 연동은 그 다음 단계입니다.
