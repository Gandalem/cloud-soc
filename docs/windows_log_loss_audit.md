# Windows 과거 로그 거절 범위 점검

## 현재 결과

### 2026-09-30 재점검

관리자 읽기 전용 검사에서 현재 진단 파일 8개, 64,338,484 bytes, 완전한 행 933개를 확인했습니다. 읽은 시각 범위는 9월 30일 09:18~11:33 KST이며, 요청한 9월 28일 13:55:40~13:56:27 KST는 관측되지 않았습니다. `evidence_state=requested_window_not_observed`, `truncated=true`, `historical_loss_count=null`, `recovery_ready=false`입니다. 기본 진단 위치와 알려진 배포본/기존 보호 복구 백업의 로그 위치에서 당시 거절 근거를 찾지 못했고, 별도 이벤트 진단 위치/이름 설정은 없었습니다. 회전·삭제의 정확한 원인은 확정하지 않았습니다.

Application·Security·System·PowerShell Operational의 OS 로그는 조회 가능하고 보존 시각 경계가 당시 진단 시점을 포함했습니다. 이는 특정 거절 이벤트가 남아 있거나 같은 내용이라는 증거가 아닙니다. 예전 보고서는 1,798이라는 집계만 남겼고 200개 참조의 실제 식별값·내용 지문은 내보내지 않았으므로 현재 동일 후보의 중앙 중복/유실을 확정할 수 없습니다.

**결론: 알려진 거절 흔적은 있으나 전체 고유 유실량과 안전한 재전송 대상은 미확정입니다.** 설정·CA·keystore 해시와 실행 정책은 전후 동일하고 Filebeat는 계속 Running입니다. 전체 재수집/큐 초기화/추정 재전송은 수행하지 않았습니다. P0C-16의 실제 복구/재수신 완료 기준은 유지하며 미완료로 남깁니다. 내부 관리자 점검이며 일반 사용자 화면을 추가하지 않습니다.

### 배포와 실제 중앙 대조

한글 커밋 `2925cb9`·`19612c2`를 푸시하고 VMware 포털에 배포했습니다. 보호 백업/검사·이전 이미지 보존 후 포털만 교체했으며, 기존 패키지 8개·키 감사 이력 17개·사건 DB의 전체 행/BLOB 동일성을 확인했습니다. PC 에이전트 재설치나 갱신은 필요하지 않습니다.

실제 monitor 읽기 조회에서 9월 28일 04:45~05:00Z 수신 창의 저장 문서 **410,824개**를 확인했습니다. 과거 거절 수와 차감할 수 있는 숫자가 아닙니다. 이미 저장된 별도 합성 검증 이벤트의 동일 참조 2개 입력은 1개로 중복 제거돼 조회됐고, 공급자를 바꾼 참조는 미조회로 반환됐습니다. 과거 거절 200개를 다시 대조한 것이 아니며 내용 동일성·재전송 검증 완료를 뜻하지 않습니다.

최종 Python 276개 통과/환경 조건 1개 제외, Node 149개 통과. CA 검증 HTTPS에서 비인증 401·관리자 화면/API 200, 12:05 KST의 품질 조회에서 최근 보고 2개와 새로운 서버 수신을 확인했습니다. Elasticsearch·Kibana·gateway는 이번 배포로 재시작하지 않았습니다.

후속 `P0C-18`은 앞으로 발생할 거절의 제한된 참조/내용 지문 보존입니다. 보존 항목·민감정보·용량·기간을 정한 뒤 검증하며, 현재 과거 근거를 소급 복원하거나 자동 재전송하는 기능이 아닙니다.

### 이전 점검 이력

2026-09-28 P0C-15의 Elasticsearch 동적 필드 한도 보존형 대응 후, 기존 Windows Filebeat는 실행 중입니다. 과거 거절 이벤트가 자동으로 되살아난 것은 아닙니다.

P0C-16 읽기 전용 점검에서 보존된 진단 파일 10개, 약 21MiB, 완전한 행 4,487개를 읽었습니다. 필드 한도 거절 기록 1,798개를 확인했고, 그중 채널/레코드 ID 참조 200개는 Windows에서 조회됐습니다. 원본 본문·채널명·호스트 식별정보는 결과에 넣지 않았습니다.

**1,798은 전체 유실량이나 고유 문서 수가 아닙니다.** 진단 파일 회전/읽기 상한·중복 진단·재시도·한도 대응 이전 기록 누락이 있습니다. 확인한 거절 기록의 시각 범위는 04:55:40.769~04:56:26.446 UTC이며, 원본 이벤트 발생 시각 범위와 다릅니다. 레코드 번호는 로그 삭제/재생성 때 재사용될 수 있어 번호 조회만으로 같은 원본임을 보장하지 않습니다. 200개 조회 성공은 복구 가능성의 단서이지 재전송 검증 완료가 아닙니다.

## 도구

관리자 승인된 로컬 점검 도구: `deploy/agents/audit-windows-loss.ps1`.

```powershell
# 관리자 PowerShell. 결과 파일은 새 이름으로 지정합니다.
.\deploy\agents\audit-windows-loss.ps1 -ResultPath .\state\loss-audit-new.json
# 특정 기간과 이전 비밀 제외 집계 보고서를 대조할 때
.\deploy\agents\audit-windows-loss.ps1 `
  -Since '2026-09-28T04:55:40Z' -Until '2026-09-28T04:56:27Z' `
  -BaselinePath .\state\p0c16-loss-audit.json `
  -ResultPath .\state\loss-audit-history-new.json
```

이 도구는 설치 경로의 일반/이벤트 오류 진단 로그만 읽고 서비스·설정·키·registry·큐·실행 정책을 바꾸지 않습니다. 전체 드라이브나 개인 문서를 탐색하지 않습니다. 원문/인증정보를 출력하거나 네트워크로 전송하지 않습니다. 운영 진단 로그에는 민감 내용이 있을 수 있으므로 원본 파일을 공개 이슈/대화에 붙이지 마세요.

상한: 이벤트 거절 진단을 우선한 최대 파일 32개, 파일당 앞부분 8MiB, 전체 64MiB, 행당 512KiB, 이벤트 참조 최대 200개, 기본 실행 시간 60초. OS 읽기 한 번의 제한 시간은 1초이며 API/디스크 지연으로 전체 벽시계 제한을 조금 넘을 수 있습니다. 마지막 불완전 행은 무시합니다. 결과의 `truncated`, `references_limited`와 `complete_loss_count=false`를 함께 해석해야 합니다. 손상·파일 접근 실패는 성공/전체 확인으로 간주하지 않습니다. 기존 결과 파일은 `CreateNew`로 덮어쓰지 않으며 진단 입력 폴더에는 결과를 쓸 수 없습니다. 기간은 명시적 시간대 포함 ISO 시각과 최대 31일로 제한합니다.

schema 2의 `prior_field_limit_entries`는 이전 집계이지 새 고유 유실량이 아닙니다. `rejections_observed_identity_unverified`는 거절 관측·동일성 미확인, `no_rejections_observed_in_read_subset`는 읽은 부분에서 거절 미관측, `requested_window_not_observed`는 요청한 기간의 근거 미관측입니다. 어느 상태도 전체 무손실이나 자동 복구를 보장하지 않습니다. PowerShell 5.1/7의 날짜 변환 차이와 실제 Elastic `+0900` 시각을 회귀 검증합니다.

## 중앙 읽기 전용 대조

포털 이미지에 배포되는 `cloud_soc.portal.loss_audit`는 기존 monitor 조회 계정과 내부 HTTPS/CA를 사용합니다. 발급/관리자 계정 권한을 넓히지 않고 패키지/사건 DB를 열거나 문서를 쓰지 않습니다.

```bash
# <collector-uuid>는 해당 수집기의 정확한 agent.id. 비밀번호나 API 키를 넣지 않음.
sudo docker exec cloud-soc-central-portal-1 python -m cloud_soc.portal.loss_audit \
  --agent-id '<collector-uuid>' \
  --since '2026-09-28T04:45:00Z' --until '2026-09-28T05:00:00Z'
```

`stored_documents_in_receipt_window`는 **서버 수신 시각**으로 조회한 실제 저장 문서 수이며, 거절 횟수나 유실량과 빼기/합산하지 않습니다. 이벤트 발생 시각·진단 오류 시각·서버 수신 시각은 별개입니다. 결과는 수집기 식별값을 해시 요약만 출력하고 본문을 반환하지 않습니다.

검증된 후보 메타데이터를 확보했다면 `--references-stdin`으로 최대 200개의 `channel`, `record_id`, `provider`, `event_code`, `occurred_at`만 전달할 수 있습니다. stdin 입력은 최대 128KiB, 전체 대조 예산은 60초이며 마지막 네트워크 요청 지연 때문에 벽시계가 조금 길 수 있습니다. 타임아웃·부분 shard 실패·정확하지 않은 집계는 실패 종료하고 불완전 결과를 성공 보고하지 않습니다. 중복 참조는 제거하며, 같은 수집기·채널·번호·공급자·이벤트 번호·발생 시각을 모두 조건으로 조회합니다. 참조 일치는 내용 동일성 증명이 아니고 미조회도 유실 확정이 아닙니다. 보호된 관리자 입력만 사용하고 실제 식별값·진단 본문을 Git/공개 대화에 넣지 마세요.

Filebeat 진단은 크기/개수에 따라 회전하며 이벤트 본문 오류는 별도 진단 파일에 기록될 수 있습니다. 정해진 보존 기간을 보장하는 기능이 아니므로 향후 거절 발생 시 보호된 참조/내용 지문을 조기에 보존하는 운영 절차가 필요합니다. 저장량과 민감정보 영향을 검토하기 전 전체 원문 진단의 장기 보존을 자동 적용하지 않습니다. [공식 로깅 설정](https://www.elastic.co/guide/en/beats/filebeat/current/configuration-logging.html), [설정 참조](https://www.elastic.co/docs/reference/beats/filebeat/filebeat-reference-yml).

## 향후 거절 근거 보존: P0C-18

새 Windows native Discovery에는 **기본 비활성**의 관리자 전용 보존 기능이 포함됩니다. 2026-09-30 후속 요청으로 VMware 포털에 새 소스를 배포하고 기존 테스트 PC의 worker를 보호 갱신한 뒤 명시 활성화했습니다. 다른 PC와 기존 ZIP에는 자동 적용되지 않습니다. 새 코드로 만든 전체 패키지의 `enable-rejection-evidence.ps1`을 명시적으로 실행해야 활성화됩니다.

2026-09-30 사용자 승인으로 조사 보조 기록의 보존 기준을 **7일 / 총 16MiB / 최대 2,000건**으로 확정했습니다. 기준 확정만으로 실제 PC에서 켜지지는 않으며, worker 갱신·명시적 활성화·운영 검증은 별도입니다. 저장 위치는 보호된 설치 폴더의 `rejection-evidence`이고 관리자·SYSTEM만 접근합니다. HMAC 키는 해당 PC에서 무작위 생성하며 API 키가 아닙니다. 키·manifest를 공개 이슈/대화/일반 사용자 화면/ZIP에 넣지 않습니다.

이 기능은 법정 대상 접속기록의 장기 보관소가 아닙니다. 최소 참조와 지문은 법정 필수 기록 항목을 대신하지 못하며, 건수/용량 한도에서 7일 이전 기록이 제외될 수 있습니다. 법정 대상 로그가 중앙에도 저장되지 않았다면 이 조사 보조 기록만으로 보존 의무를 충족했다고 판단하지 않습니다.

보존 항목은 수집기 UUID·채널·레코드 번호·공급자·이벤트 번호·발생/거절 시각, 보호 처리된 이벤트의 HMAC 지문과 중복 식별값입니다. Windows 렌더링 본문·Meta·알려진 비밀 필드/값은 지문 전 제거/마스킹하고, 이벤트 내용 자체는 파일에 쓰지 않습니다. 지문은 `redacted-canonical-json-hmac-sha256-v1` 규약이며 기존 Beat 개인정보 처리 결과나 OS 원본 전체와 자동 동일성을 증명하지 않습니다. 참조 시각은 UTC 마이크로초로 정규화하므로 더 정밀한 원본 시각은 지문과 별도로 취급합니다.

주기 실행은 기존 Filebeat 진단에서 현대식 JSON 이벤트를 포함한 HTTP 400 거절만 읽습니다. 실제 9.5.2의 JSON 뒤 줄바꿈/Meta 구분자를 검증했습니다. 구형 Go 구조 문자열, 다른 상태 코드, ASCII 허용 범위 밖 채널/공급자, 손상/과대 행은 저장하지 않으며 부분 검사로 기록합니다. 임의 prose의 레코드 번호만 추출해 복구 대상으로 만들지 않습니다. 기본 진단 위치 밖의 커스텀 경로는 자동 탐색하지 않습니다.

읽기 상한은 파일 후보 열거 64개, 거절 진단 우선 실제 8개, 파일당 끝부분 8MiB, 전체 16MiB, 행 512KiB, 처리 예산 5초입니다. 디스크 호출 자체의 지연은 벽시계 예산을 넘을 수 있습니다. 새 기록과 중복 제거 결과를 잠금/신규 임시 파일/강제 flush/원자적 교체로 저장합니다. 건수 한도에서 더 최근 기록을 우선하고, 일부 건의 제외를 표시합니다. 기존/새 snapshot 동시 공간을 예약해 총량을 제한합니다.

보존 기간은 **worker가 실행될 때** 거절 시각 기준으로 정리합니다. PC/작업이 중지되면 정확히 7일 뒤 즉시 삭제되는 것이 아니며, 운영·복구 백업은 별도의 승인된 보존 정책이 필요합니다. 시계 역행·손상·다른 키·링크/하드링크·예상하지 않은 파일·잠금/교체/정리 실패에는 기존 자료를 덮어쓰거나 자동 초기화하지 않습니다. 오류는 `rejection_evidence.state=error`, 한도/미지원은 `scan_partial=true`로 내부 health 보고에 기록하되 기존 Discovery/로그 수집을 중단시키지 않습니다. 어느 집계도 전체 유실량·전체 무손실을 뜻하지 않습니다.

```powershell
# 보존 기준은 확정됐으며, 실제 활성화 요청 및 새 worker 갱신 이후 관리자 PowerShell에서만 사용합니다.
# 현재 PC에 자동 실행한 명령이 아닙니다.
.\enable-rejection-evidence.ps1 -DryRun
.\enable-rejection-evidence.ps1 -ApproveRetention
```

기존 store가 있으면 키 재발급/삭제/덮어쓰기를 거부합니다. 부분 준비 실패의 보호 staging은 무조건 삭제하지 않습니다. 잠금이 사용 중이면 worker를 강제 종료하지 않고 다음 실행 때 재시도합니다. 보존 기준은 확정됐지만 실제 활성화 후 신규 거절의 참조를 OS/중앙과 대조하고 운영 수신 보존을 검증하기 전까지 **P0C-18 전체 완료로 처리하지 않습니다**. 자동 재전송/새 UI/일반 사용자 복구 절차는 추가하지 않았습니다.

## 안전한 복구의 선행 조건

참조 비교는 호출자가 수정할 수 없는 source 기반 runtime keyword 필드를 사용합니다. 기존 공급자 필드가 text/keyword로 다르게 매핑됐거나 필드 한도 초과로 검색에서 제외돼도 저장된 메타데이터를 비교하며, 클러스터 매핑을 바꾸지 않습니다. 수집기 ID와 발생 시각은 먼저 범위를 좁힙니다. 일치 여부는 어디까지나 참조 메타데이터의 일치이고 전체 내용 동일성이나 중복 제거 완료가 아닙니다.

1. 대상 호스트·조직·채널·기간을 정하고, 진단에서 확보한 후보와 OS 원본의 공급자·ID·발생 시각·레코드 번호·내용 지문을 대조합니다. 번호가 같다는 이유만으로 재전송하지 않습니다.
2. 중앙에 이미 도착한 원본 참조와 비교해 중복을 구분합니다. 과거 문서는 자동 ID로 저장됐으므로 단순 새 ID 쓰기는 기존 문서와의 중복 방지를 보장하지 않습니다.
3. 승인된 후보만 별도 복구 manifest로 고정하고, 기존 `privacy.js`와 동등한 보호 처리를 실제 Beat 경로에서 검증합니다. 원본 내용을 보존하지 못했거나 식별이 불확실한 후보는 자동 전송하지 않습니다.
4. 작은 묶음으로 재개 가능한 재전송과 별도 복구 ID를 적용하고, 실제 중앙 도착·원본 참조·중복 거부·실패 재개를 검사합니다.

현재 자동 재전송 도구는 구현/실행하지 않았습니다. 큐/registry 초기화, 기존 OS 로그 삭제, 감사 정책 완화, 전체 로그 재색인으로 우회하지 않습니다. 초기 과거 수집 범위·보존 기간·초과 필드의 검색 정책은 별도 합의가 필요합니다. 신규 이벤트의 정상 수신과 과거 유실 복구는 다른 완료 기준입니다.
