# P6 사건 조사와 업무 저장

코드·로컬 UI·격리 Elasticsearch 검증 안내입니다. 이 작업에서 AWS/OCI 운영 배포, 실제 에이전트 설치, 탐지 규칙 활성화는 수행하지 않았습니다.

## 사용 순서

1. 관제 메인의 실제 경보 상세에서 **사건 조사 / 등록**을 선택합니다. 제목과 우선순위를 입력하고 명시적으로 사건을 생성합니다. 단순 조회로 사건이 생기지는 않습니다.
2. **사건 업무 큐**에서 상태·담당·우선순위·생성 기간·정렬을 선택합니다. 집계와 목록은 동일한 필터를 사용합니다. 이 기간은 로그/경보 조회 기간과 별개입니다.
3. 조사 화면에서 연결 경보를 열어 탐지 이유, 대상, 원본/정규화 참조와 일치 근거 메타데이터를 확인합니다. 전체 원문과 민감 본문은 계속 제한됩니다.
4. 담당을 현재 관리자에게 배정하고 상태·판정·메모를 저장합니다. 추가 경보 ID를 입력해 같은 조직의 경보를 연결할 수 있습니다. 하나의 경보는 하나의 사건에만 연결됩니다.
5. 종결에는 판정과 사유 메모가 필요합니다. 종결 사건은 사유를 입력하고 **조사 중**으로 재개해야 수정할 수 있으며, 판정은 미검토로 돌아갑니다.
6. 목록으로 돌아가면 사건 필터가 복원됩니다. 사건의 변경 이력에는 작성 계정·시각·버전·변경 전후 값·메모가 남습니다.

연결 경보의 시간순 목록은 전체 활동 타임라인이 아닙니다. 주변 활동은 통합 로그에서 별도로 조사하며, 일치 근거로 자동 편입하지 않습니다. 만료된 ES 경보/근거는 조회 실패와 구분합니다. 저장 당시 경보 메타데이터는 사건에 남지만 이를 현재 ES 조회 결과로 표시하지 않습니다.

## 저장과 권한

- 사건·연결·메모·판정·이력·재시도 기록은 `STATE_DIR/cases.sqlite`에 저장합니다. 중앙 Compose 기본 경로는 호스트 `state/server/portal/cases.sqlite`, 컨테이너 `/data/cases.sqlite`입니다. 사용자 지정 상태 경로를 쓰면 그 경로가 기준입니다.
- 현재 포털의 단일 관리자 인증 범위입니다. 담당은 미배정 또는 해당 관리자뿐입니다. 다른 조직 경보 연결은 막지만, 관리자에게 조직별 읽기 권한을 분리하는 다중 사용자 RBAC는 아닙니다.
- 작성 주체는 인증에서 결정하며 요청 본문으로 위조할 수 없습니다. 공용 관리자 계정을 여러 사람이 쓰면 실제 사람을 구별할 수 없습니다.
- ES 원본/경보는 읽기 전용입니다. 사건 저장을 위해 ES 쓰기 권한이나 새 탐지 규칙을 추가하지 않습니다.
- 메모와 제목의 길이·입력 형식을 검사하고 알려진 비밀정보 패턴은 거부합니다. 이는 완전한 DLP가 아닙니다. 비밀번호·키·개인문서 본문을 입력하지 마세요.
- 이력 수정/삭제 API는 없습니다. 그러나 SQLite 파일에 접근하는 서버 관리자의 변조까지 막는 감사 저장소는 아닙니다. 호스트 접근 통제와 별도 백업이 필요합니다.

## API와 동시 수정

| 경로 | 용도 |
| --- | --- |
| `GET /api/cases` | 필터·정렬·페이지·일치 집계 |
| `POST /api/cases` | `title`, `priority`, `alert_id`로 명시적 생성 |
| `GET /api/case-link?alert_id=...` | 기존 사건 연결 확인 |
| `GET /api/cases/<id>` | 사건·연결 경보 메타데이터·최근 이력 |
| `PATCH /api/cases/<id>` | `version`과 상태/담당/우선순위/판정/메모/추가 경보 |

쓰기는 JSON, `X-Cloud-SOC: portal`, `Idempotency-Key` 헤더와 기존 Host/Origin 검사를 적용합니다. 브라우저가 요청마다 UUID를 생성합니다. 같은 작업의 불확실한 재시도는 같은 키를 재사용하고, 키를 다른 작업에 재사용하면 409입니다. 같은 페이지에서의 재시도만 기억하며 브라우저를 닫은 뒤 재전송을 자동 보장하지 않습니다.

저장 버전이 바뀌면 409로 거부하고 작성 중인 메모를 유지합니다. 다시 조회해 최신 내용과 비교한 뒤 저장하세요. SQLite 쓰기는 직렬화되며, 잠금/저장 실패는 503으로 반환합니다. 단일 서버·소규모 사용 기준으로 대규모 동시 처리나 다중 포털 호스트 공유 DB는 검증하지 않았습니다.

한 사건당 경보 100개, 목록 페이지 25개, 이력 페이지 50개입니다. 이력은 `before` 커서로 과거 페이지를 조회합니다. 사건 목록은 offset 방식이므로 다른 사용자가 추가/수정하는 동안 페이지 경계가 바뀔 수 있습니다. 한 응답의 집계/목록은 같은 읽기 트랜잭션이지만, ES 조회와 SQLite 저장은 분산 트랜잭션이 아닙니다.

## 기존 중앙 서버 반영

변경 코드가 서버에 전달된 뒤 실행합니다. 커밋·푸시 전 로컬 변경은 `git pull`로 전달되지 않습니다. P5 조회 권한/인덱스 준비가 아직 없다면 먼저 [P5 가이드](processing_operations.md)의 bootstrap 갱신을 진행하세요.

```bash
sudo docker compose --env-file state/server/compose.env -f deploy/server/compose.yaml build portal
sudo docker compose --env-file state/server/compose.env -f deploy/server/compose.yaml up -d --no-deps portal
```

기존 portal 상태 마운트를 유지합니다. `state` 삭제나 `down -v`는 하지 않습니다. 반영 후 사건 생성·메모 저장·포털 재기동·이력 재조회로 운영 영속성을 별도 확인하세요. 자동 DB 이행/초기화/삭제 기능은 추가하지 않았습니다.

백업에는 [포털 DB 백업·격리 복원 도구](portal_backup.md)를 사용하세요. 실행 중 DB 파일만 임의 복사하지 않습니다. 도구는 새 경로 복원까지만 수행하며, 운영 교체 전에는 포털 중지·기존 파일 보존·접근 권한 확인이 필요합니다. 예약 백업과 운영 복구 시험은 미완료입니다. ES 보존 만료 후에도 사건 메타데이터와 메모가 남으므로 별도의 업무 기록 보존 정책이 필요합니다.

## 검증과 남은 범위

`tests/test_cases.py`, `tests/p6_live_checks.py`, `prototype/tests/cases.test.cjs`에서 중복 요청·재시작·실제 동시 수정·인증/CSRF·상태 전이·메모 보호·페이지·집계·ES 경보 만료를 검증합니다. `tests/preview_cases.py`는 loopback 전용 합성 UI fixture이며 운영 서버가 아닙니다.

- 완료된 로컬 범위: 별도 업무 저장, 실제 참조 기반 조사, 한국어 UI, 담당/메모/판정/이력, 사건 목록과 필터 복귀.
- 남은 P6 범위: 전체 미분류 경보 집계, 전체 원문 공개를 위한 보호 정책, 주변 활동/전체 이벤트 타임라인, 다중 사용자 권한 분리.
- 운영 확인 필요: 실제 AWS 서버 배포·백업/복구·디스크/동시 처리 성능·실제 에이전트 E2E.
- 규칙은 기존 승인 대기 상태입니다. 사건의 인계 상태는 상태 기록일 뿐, 이메일/SMS 전달이나 외부 티켓을 생성하지 않습니다.
