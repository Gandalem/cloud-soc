# 2026-10-21 탐지 중단: 날짜 정밀도 경계

## 확인된 원인

사용자가 제공한 실행 기록에서 normalizer는 최신 구간까지 성공했지만 detector는
`2026-10-19T07:56:47.618125+00:00` 체크포인트에서 반복 실패했다.
해당 탐지기의 15분 중복 조회 시작은 `2026-10-19T07:41:47.618125Z`이다.

실제 Elasticsearch 조회에서 `cloud_soc.normalized_at` 필드 타입은 `date`였고,
위 시작 시각의 `gte` 조건에도 `_source`가 `2026-10-19T07:41:47.618105Z`인
문서가 반환됐다. 인덱스 정렬 값은 밀리초였지만 원본에는 마이크로초가 남아 있었다.
기존 `staging.add`는 이를 `outside_receipt_range`로 거부해 트랜잭션을 롤백했다.
따라서 입력 건수는 0이고 체크포인트가 계속 같은 곳에 남았으며,
외부에는 일반 `incremental_cycle_failed`만 표시됐다.

Elasticsearch의 `date`는 밀리초로 저장된다:
https://www.elastic.co/docs/reference/elasticsearch/mapping-reference/date

## 수정 동작

- 조회 시작은 밀리초 내림, 끝은 밀리초 올림으로 후보 버킷 전체를 읽는다.
- 원본 시각으로 정확한 `[lower, end)` 범위를 적용한다. 인접 구간 후보는 spool에 넣지 않는다.
- 후보 버킷 자체를 벗어난 응답, 잘못된 참조, 불완전 조회는 기존처럼 실패 처리한다.
- 기존 부분 조회의 PIT/search_after는 같은 고정 구간에서 한 번 다시 시작한다.
  기존 spool·seen·체크포인트와 선택한 규칙/출처 정체성은 유지한다.
- 오류 원인은 고정된 코드로 상태 문서와 콘솔에 전달한다. 서버 오류 본문,
  API 키, 로그 원문 또는 파일 경로를 오류 문자열로 출력하지 않는다.

## 로컬 확인과 적용 구분

영향 범위 검사 33항목과 3개 subtest가 통과했다. 실제 날짜 값으로
밀리초 검색 모델·원본 경계 판정·체크포인트 진행·기존 커서 재조회·재시작·PIT 만료·
권한 실패 후 재시도와 상태 보존을 확인했다. 변경 파일 Ruff 검사도 통과했다.
전체 suite나 운영 Elasticsearch에 대한 쓰기 검사는 수행하지 않았다.

운영 배포, 컨테이너 재시작, 키/규칙/체크포인트 변경은 수행하지 않았다.
적용 시 detector, detector-priority, detector-additional이 같은 수정 이미지를
사용해야 한다. 원인 해결을 위해 상태 DB를 삭제하거나 초기 시작 시각을 바꿀 필요는 없다.
기존 보류 구간을 처리하므로 밀린 기간에 따라 따라잡는 시간이 필요하고,
이미 최종 처리 시각을 지난 이벤트는 기존 지연 처리/과거 재평가 정책을 따른다.
수정 자체가 과거 경보의 Slack 전송이나 모든 데이터의 위험 평가 완료를 보장하지 않는다.

적용 후 각 탐지기의 checkpoint가 진행하는지, failed가 해소되는지,
새 경보가 생성되는지와 Slack 전송 상태를 각각 확인해야 한다.
별도 enrollment-cleanup 컨테이너의 재시작은 이 날짜 경계 장애와 분리해서 다룬다.
