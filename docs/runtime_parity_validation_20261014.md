# 2026-10-14 공통 런타임·집 서버 인수 결과

집 서버 `192.168.235.128`의 보호 업그레이드, 실제 워커 재시작, 공통 구성에서의 재업그레이드, 실제 AUTH-001 로그→정규화→최종 경보→대시보드 인수를 통과했다. 신규 설치/실패 복구는 Windows·Linux 격리 시험을 인수 근거로 사용한다는 사용자의 최종 지시를 따랐다. **빈 Ubuntu 실서버 신규 설치와 다른 중앙 `192.168.32.60`의 실제 적용은 미검증**이다. 별도 VM을 만들지 않았으며 다른 중앙에는 접속 확인 외 변경을 하지 않았다.

## 변경 내용

- `deploy/server/compose.yaml`과 공유 fragment가 포털·정리 작업·ES·Kibana·게이트웨이 및 필수 워커 6개를 선언한다. 워커는 normalizer, normalizer-priority, detector, detector-priority, detector-additional, detector-retrospective다.
- `runtime-policy.json` 버전1과 `001-permissions-and-indices`/`002-independent-workers` 마이그레이션이 같은 설치/업그레이드 진입점에서 실행된다. 미래 버전·알 수 없는 명령/상태·제약된 권한·기존 identity 변경을 거부한다. 신규 설치에만 초기 계정 bootstrap을 실행한다.
- 기존 시작점·SSH adapter floor·frontier·미완료 상태·초기 통지 sidecar/outbox를 온라인 백업으로 인수한다. 원래 DB는 남긴다. 기존 키 ID/토큰/만료·계정/인증서·CA·사이트 주소/mount를 보존하고 필요한 제한된 권한만 추가한다.
- 수동 Docker 실행, 다른 Compose project, 이름 변경/scale 복제 워커를 발견하면 적용 전에 중단한다. 기존 수동 실행을 임의 삭제하지 않는다. 실제 기동 후에도 필수 워커가 정확히 하나씩 존재하고 같은 앱 이미지인지 검사한다.
- 계획과 후보의 실제 파일 해시·이미지 ID·기존 구성/보호 파일/권한을 적용 직전에 다시 검사한다. 버전 ledger와 중단 journal을 남기며 `recover`는 DB를 되감지 않고 이전 실행·계약·영수증을 복구한다. 최종 영수증 쓰기 직후 실패와 KeyboardInterrupt도 시험했다.
- 관리자 `/api/runtime`, 독립 priority 탐지 상태와 대시보드, 실제 입력이 없으면 통과하지 않는 API/정규화/탐지/포털 인수 도구를 추가했다. [운영 절차](runtime_deployment.md).

## 거부안·SQLite·보존 확인

자동 승인에서 거부됐던 운영 SQLite 디렉터리의 preflight 컨테이너 RW mount는 반영하지 않았다. `contract.py`의 자원/룰 gate와 `host.py`의 실제 구현을 확인하고, **호스트의 SQLite online backup API → 독립 사본 → 컨테이너 RO mount**로 보완했다. 마이그레이션의 명시적 운영 상태 쓰기 mount와 읽기 전용 사전 검사는 구분한다.

격리 WAL 시험은 본 DB에 아직 checkpoint되지 않은 커밋을 만든 뒤 백업의 값을 대조했다. 원래 DB/WAL 바이트와 운영 WAL 모드는 그대로였고, 사본만 standalone DELETE journal로 변환해 RO 읽기·무결성·memory restore를 검증했다. 운영 DB에 강제 WAL checkpoint/truncate를 실행하지 않았다.

실제 첫 적용은 기존 불변 경보2개와 사건/저장 대시보드 관련7행을, 재업그레이드는 당시의 불변 경보/통지4문서와 같은7행을 보존 검사했다. 기존 인증/키/CA/사이트 파일의 해시도 대조했다. 신규 경보나 새 로그는 추가되며 기존 문서를 지우거나 덮어쓰지 않는다.

검증용 SQLite 사본이 운영 상태 경로에 들어가 다음 백업 예산에 포함되는 것을 확인해 별도 보호 경로로 이동했다. 이 사본13개만 무손실 압축했고, 압축 해제 SHA가 원래 바이트와 일치함을 확인했다(489,299,968 → 8,729,710 bytes). 운영 DB와 실제 업그레이드 보호 사본은 삭제하지 않았다. 디스크 부족 검사 자체는 유지했으며 공간 확보 후 다시 계획했다.
