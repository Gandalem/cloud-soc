# 상시 처리와 AJAX 갱신

## 승인 범위와 실행 순서

2026-10-20 사용자 승인 초안을 구현한다. 구현 중 테스트/린트/빌드/실행 검사는 하지 않는다.
코드·화면·실습 설치/복구 도구·인수 도구 작성 완료 후 최종 검수를 모아서 수행한다.
실패 수정 후에는 영향 구간만 재검사하고, 검수가 끝난 뒤 실습 VM을 실제 재부팅해 흐름을 확인한다.
이 문서의 설계/도구 존재와 실제 검수·배포·재부팅 인수 결과는 별개다. 결과는 작업 목록에 기록한다.

## 처리 계약

`processing.scoped_service`는 exact source/output 인덱스·별도 상태 파일·명시적 수신 시작 시각을 받는다.
history는 기존 initial_start/원본 인덱스 순서/저장 인덱스/SQLite 상태를 유지한다.
receipt 정책은 기존30초/900초 겹침으로 고정하며, 과거 상태를 우선 처리용으로 변경하지 않는다.
과거 범위를 최대60분씩 읽고 페이지 예산 내 최대3회 연속 처리한 다음 양보한다.
기존 partial PIT 범위가 있으면 먼저 끝낸다. 부분 실패에서 coverage 체크포인트를 전진시키지 않는다.

recent는 별도 상태와 최초 배포 시 고정한15분 전 수신 시작점을 사용한다.
재부팅에도 이 시작점과 진행 상태를 재사용한다. 조회 주기2초·receipt 여유2초·겹침900초다.
동일 원본·정규화 버전은 기존 안정적 ID와 create-only 쓰기로 중복을 막는다.
기존 문서를 다른 경로의 처리 시각으로 덮어쓰지 않는다. 경보도 기존 관리 규칙 identity/불변 저장 계약을 유지한다.
페이지/항목 예산을 넘기거나 인증·연결·저장이 실패하면 실패를 보고하고 상태에서 재시도한다.

900초를 넘는 검색 가시성 지연/수신 시각 변조 등 모든 장애의 무손실을 보장하지 않는다.
허용 범위 밖 이벤트 시각은 기존 관리 워커의 지연/미래/미지원 이력으로 보존하며 정상 완료/경보0으로 숨기지 않는다.
원본 바이트의 독립 WORM/hash 보관·HA·호스트 손실/백업 복원은 이번 변경 범위가 아니다.

## 상태 보고와 권한

명시적 `PROCESSING_SCOPE`와 `MANAGED_WORKER_CONFIG`를 받은 Portal만 해당 원본/정규화/경보 범위와
정확히 일치하는 처리 상태를 연결한다. 환경 설정은 `SOC_PROCESSING_SCOPE_FILE`,
`SOC_MANAGED_WORKER_CONFIG_FILE`의 소유자 전용 JSON으로도 전달할 수 있다.
설정이 없으면 기존 동작을 유지한다. wildcard/범위 불일치를 자동 수용하지 않는다.

관리 워커는 동일 SQLite에 config identity별 heartbeat를 저장한다. Portal은 읽기 전용 연결로만 조회한다.
보고45초 만료·실패·적용 대기·문제 입력·실행 규칙0개를 구분한다.
실행 규칙이 없으면 워커 프로세스 생존을 분석 완료로 표시하지 않는다.
최근/과거 정규화와 관리 탐지 상태를 각각 표시하고, 조직 제한 계정에 전역 상태/처리 기록을 노출하지 않는다.
관리 키·장치 등록/설치·역할 API는 데이터 reader 계정으로 우회하지 않는다.

## 화면 공통 계약

`live-refresh.js`가 요청 취소·순서·시간 제한·비활성 탭·오류 후 재시도·일시정지·수동 갱신을 담당한다.
일반 조회10초 주기이며 비활성 탭에서는 취소/대기하고 돌아오면 새 조회를 시작한다.
숨김/일시정지/새 요청 이후 이전 응답은 화면에 적용하지 않는다.
오류가 나면 마지막 성공 시각과 갱신 실패를 표시하고 마지막 확인 내용을 유지한다.

대시보드/관제의 수치와 차트는 부분 갱신한다. 새 경보 목록은 버튼에 모아 사용자가 반영한다.
개인 대시보드는 편집 중 자동 조회를 보류하고 자동 조회에서는 위젯 내용만 변경한다.
공통 DOM 패치는 같은 키의 노드·키보드 포커스·입력값·펼친 details를 보존한다.
규칙 작성 중 입력은 건드리지 않고 실행 상태와 읽기 전용 상세만 갱신한다.
사건 목록은 새/변경 항목을 알리고 사건 상세는 새 내용 별도 창을 안내해 미저장 메모를 보호한다.

로그 목록은 기존 PIT 페이지와 별도의 `/api/logs/updates` head 미리보기를 사용한다.
미리보기는 같은 필터/조직 권한/형식 검사 후 PIT를 닫고 paging cursor를 발급하지 않는다.
페이지를 보던 중 새 head를 기존 search_after에 섞지 않는다.
검색 조건을 편집 중이면 자동 조회를 보류한다. 고정 시간 조회는 고정 범위를 유지한다.
실시간 따라보기는 사용자가 켰고 첫 페이지/상세 창 닫힘일 때만 새 스냅샷으로 바꾼다.

## 접속·남은 조건

현재 Windows에서는 host key를 확인한 SSH loopback forwarding으로
`http://127.0.0.1:18081`(Portal), `:18080`(쇼핑몰), `:18082`(WAF 경유)에 접속한다.
기존 사용자 설정으로 복구했으며 새 관리 비밀번호를 PC로 복사하지 않았다.
이 연결은 현재 Windows 세션의 보조 프로세스이며 Windows 재부팅 후 자동 연결까지 구성한 것은 아니다.
VM 서비스 자동 기동과 PC 터널 자동 기동은 구분한다. 외부 공개/방화벽 변경/운영 배포는 하지 않았다.

- 90일 상시 키의 만료 전 교체와 같은 권한 검사를 별도 관리해야 한다. 기존 Portal 부팅 guard도
  원래 reader 설정에 의존하므로 이후 원래 키를 폐기/만료시키기 전에 guard 연결까지 함께 갱신해야 한다.
- 단일 VM/ES와 로컬 SQLite다. HA·VM 손실·디스크 손실·백업 복구·인증 키 부활 방지를 검증하지 않았다.
- 현재/과거 조회 겹침은900초다. 그보다 긴 검색 가시성 지연을 무손실 보장으로 해석하지 않는다.
- 실습 파일 수집기는 실제 사용했으나 Windows/Linux 전체 장치 설치·배포, 모든 출처/규칙 조합,
  Slack 외부 전송·모든 사건 편집 동작·장시간 부하까지 이번 화면 인수로 완료했다고 표시하지 않는다.
- 새 점수 산식/기존 경보 점수 변경은 범위 밖이다. 심각도와 계산 위험 등급은 서로 다르며
  관리 규칙의 계산 위험은 기존 미평가 계약을 유지한다.

다음 인수는 사용자가 유지할 실제 규칙 세트의 선택/적용과 대표 입력의 장시간 지연·적체 측정,
키 교체/guard 갱신·복구 절차다. 개발 중 검수 빈도는 사용자의 이후 지시를 따른다.
