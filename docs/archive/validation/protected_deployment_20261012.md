# VMware 보호 배포와 실제 수신 검증 — 2026-10-12

후속 현재 상태: 사용자의 보호 배포·복구 승인으로 고객용 포털/정규화 개선을 적용하고 최근 수신 구간까지 실제 이어 처리·중단 복구·ES/API/브라우저를 대조했다. 제외 1건 등 운영 인수는 남는다. 아래 정체·현재 상태 유지 설명은 앞선 검증 시점 이력이며 [후속 실제 결과](customer_readiness_20261012.md)를 별도로 보존한다.

사용자가 지정한 Ubuntu `192.168.235.128`과 Windows `192.168.235.130`을 대상으로 서버·수집기·키 상태 점검, 보호 백업, 최신 main 배포와 대표 실제 수신을 수행했다. 서버 배포와 네 수집기의 ES/API 수신은 검증했지만 **정규화가 읽기 상한에 정체돼 전체 처리·탐지 운영 인수는 미완료**다. 사용자 선택에 따라 추가 수정의 실제 적용은 보류했다.

- 새 실험 공격 프로필을 활성화하지 않았다. detector는 기존 기본 `AUTH-001`, 지연 허용 900초로 실행한다.

사용자의 명시적 승인으로 `admin` 포털 비밀번호만 변경하고 원래 로그인 해시를 보호 백업했다. VM의 OS 로그인과 enrollment 자료는 변경하지 않았다. 새 비밀번호를 이용한 CA/주소 검증 HTTPS 인증·API 조회·실제 설치 파일 다운로드를 통과했다. 비밀번호는 별도 사용자 안내에서 전달하며 파일에 저장하지 않았다.

## 네트워크와 수집기 갱신

Ubuntu의 기존 Docker bridge에 네트워크 메타데이터가 선언한 `172.18.0.1/16` 주소가 빠져 SSH 외의 포털/ES 접속이 막혔다. 해당 bridge 주소만 복구하고 방화벽 규칙을 시각/카운터 제외 기준으로 대조했다. 처음의 원시 파일 비교 실패와 후속 규칙 동등성 결과를 모두 보존했다. VM 재부팅 후 이 주소의 지속성은 이번에 시험하지 않았다.

호스트 키 항목은 `CLOUD_SOC_API_KEY`, 네트워크 키 항목은 `CLOUD_SOC_NETWORK_API_KEY`다. 갱신 도구의 초기 네트워크 항목 혼동으로 401을 확인한 뒤 전용 항목으로 바로잡았고, 원래 없었던 임시 잘못된 항목만 제거했다. 두 운영체제 네 수집기의 config/output·엄격 CA/주소 검증을 통과했다. 비밀 값은 핀을 대조한 SSH 연결의 메모리/표준 입력으로 전달했으며 로컬 파일·명령 인자에 저장하지 않았다.

Ubuntu는 최신 `discover-linux.sh`·`collector-metrics.py`, Windows는 최신 패키지의 `discovery-native.cs`를 서명 유효한 Microsoft .NET Framework 컴파일러로 빌드한 네이티브 worker를 적용했다. 원래 worker 파일·ACL·설정을 보호했다. Windows 실행 정책 Restricted는 유지했고 SYSTEM 예약 작업의 실제 실행 결과 0·새 보고·두 서비스 Running을 확인했다. Ubuntu 두 서비스·Discovery timer도 active다.

Windows Packetbeat 큐 세그먼트/registry/ID의 바이트는 유지됐으나 확인 구간의 ACK 커서가 9,840프레임 앞으로 이동했다. 이전/현재 커서를 모두 보관하고 해당 시각 중앙에서 10,353건의 수신을 확인했다. 커서를 임의로 되돌리거나 큐를 삭제하지 않았다. 전체 ACK 프레임과 ES 문서를 1:1 전수 대조한 것은 아니므로 전체 무손실을 주장하지 않는다.

## 실제 ES → API 대조

실제 운영체제와 NIC를 통해 생성·수신된 대표 자료다. ES에 시험 이벤트를 직접 쓰지 않았다.

| 대상 | 근거와 결과 |
| --- | --- |
| Ubuntu 호스트 | `logger` 시험 표식, 발생 08:07:26.559 UTC·서버 수신 08:07:26.838 UTC, 기존 ID/조직 대조. 같은 표식 검색은 2건이며 전수 중복 원인 분석을 완료한 것은 아님 |
| Windows 호스트 | Application 기록 번호 1513·이벤트 ID 777·provider Cloud-SOC-Deployment·발생 08:28:17.884 UTC와 실제 문서의 필드 일치, 수신 08:28:55.327 UTC |
| Windows 네트워크 | 실제 `192.168.235.130:62414 → 192.168.235.128:9200` 연결을 해당 Packetbeat ID에서 수신 |
| Ubuntu 네트워크 | 같은 연결의 주소/포트/시각을 별도 Ubuntu Packetbeat ID에서 수신 |

네 대표 참조의 인증된 `/api/logs/detail` 응답과 ES index/ID·조직이 일치하고 `raw_access=restricted`를 확인했다. Packetbeat는 recognized, 일반 시험 logger/Application 이벤트는 unsupported이며 위험 탐지 성공으로 표시하지 않는다. Windows 검색은 기록 번호가 채널마다 중복될 수 있어 반환된 provider·이벤트 ID·발생 시각까지 대조했다. 첫 엄격 provider term 조회의 0건을 후속 실제 필드 조회와 구분해 보존했다.

동일 생성 시각의 호스트/네트워크 계측 26개 숫자 필드를 각 VM의 로컬 보고 → ES → 인증된 `/api/agents/health`에서 대조했다. Windows 생성 `08:33:34.163720 UTC`, Ubuntu 생성 `08:33:59 UTC` 표본의 숫자·표본 시각이 일치했다. 미보고 수치는 null을 유지한다. 당시 네트워크 output 읽기 오류와 일부 마지막 문제 표본이 존재해 API는 `error_observed`를 반환한다. 정상 0으로 바꾸지 않았다. 로컬 통계의 제한된 스캔/누락·입력별 경고·전수 유실 분석은 P2-03 잔여다.

포털 주요 HTML·API는 실제 HTTPS 200과 최신 파일 해시를 확인했다. **이번 최신 배포의 실제 브라우저 렌더링·모바일 화면 대조는 하지 않았다.** 과거 화면 검증 이력과 이번 결과를 구분한다.

## 정규화 정체와 미적용 수정안

처리 시작점은 배포 당시 `2026-10-12T07:25:51Z`다. 이보다 이른 수신 문서를 별도로 소급 처리하지 않았다. 과거에 발생했지만 만료 키 때문에 큐에 있다가 배포 후 새로 수신된 문서는 기존 수신 시각 계약상 신규 처리 대상이다. 처리 결과는 create-only이며 과거 ES 원본의 삭제/덮어쓰기와 별개다.

초기 실제 정규화 결과·처리 기록·탐지 실행 이력이 생성됐고 기본 detector 체크포인트가 전진했다. 이후 normalizer 체크포인트가 `08:30:03.895602 UTC`에서 정체했다. 대상 중첩 구간 `08:15:03.895602~08:35:03.895602 UTC`에는 338,643건이 있었다. 본문을 요청하지 않는 실제 읽기 전용 scanner가 200,000건 후 **`window_page_limit`**을 재현했다. 서비스가 실행 중이라는 이유로 정상 처리라고 보고하지 않는다. detector도 제외 1건을 warning으로 표시하며 실제 위험 시나리오 경보 인수는 남았다.

로컬 수정안은 CLI `--max-pages`와 Compose `SOC_PROCESSING_MAX_PAGES`를 추가한다. 기존 기본 1,000페이지·페이지/쓰기 배치 크기·시작점·체크포인트·create-only 규칙은 유지한다. 1~10,000 정수만 허용한다. 상한 초과 후 체크포인트 보존·PIT 정리·예산 증가 재개·이미 생성된 결과의 409 처리·중복 개수 불변·CLI 검증/연결·다중 인덱스 시험을 포함해 **29 tests·7 subtests 통과**, 변경 Python Ruff 통과, Compose 기본 옵션 검사 통과를 확인했다. 초기 잘못된 시험 파일명/의존성 경로 실패를 후속 성공과 구분했다.

시험 후보 이미지는 `sha256:549d6693f3add7bec7f8df10bd6d4ee3c6482c4e83882cf342b72019e988539df`, 수정 소스 해시 `8bb1fd443f170ae36abc77916397cef5ddd2351ae8ee331f7444d795fd206c62`다. 실제 데이터 접속 없이 5,000페이지 설정/소스 해시를 확인했다. 후보 빌드와 오프라인 검증은 실제 배포·처리 복구 증거가 아니다.

자동 승인 검토는 실제 `run_once` 재시도 진단을 문서 재처리/체크포인트 변경 가능성으로 거절했고 해당 실행은 수행하지 않았다. 더 안전한 읽기 전용 대조로 원인을 확정했다. 구체적인 수정안/시험 이미지 준비 후 시험 서버 5,000페이지 적용·신규 수신 구간 재시도 승인을 요청했지만 사용자가 **현재 상태 유지**를 선택했다. 실행 normalizer 이미지 `22a0…`·원래 명령·기본 상한을 유지하고 후보를 활성화하지 않았다. 기존 정규화 워커의 자동 재시도 설정도 이번 선택 후 변경하지 않았다.

## 남은 순서

1. 사용자 선택이 바뀌면 준비된 정규화 상한 수정의 실제 적용·보호된 재시도·체크포인트 전진·중복 불변 검증. 상한을 늘리는 방식은 임의의 대규모 적체를 자동 분할/재개하는 일반 해결책이 아니다.
2. P2-03의 전송 오류·입력별 경고와 미측정/중복을 분석하고 최신 로그인 브라우저에서 동일 숫자·오류 상태를 대조한다.
3. P3-01/P5-03/P5-05 실제 SSH/PAM 정상·의심 시나리오 → 정확한 경보 근거/화면, P6/P7 사건·메모·재시작 보존 인수.

상위 P0-02·P2-03·P5-01/02는 잔여 인수 조건을 유지하며 완료 체크를 추가하지 않았다. 독립 백업/보존 정책·AWS 실제 자원·새 공격 프로필 활성화는 이번 결과로 완료 처리하지 않는다.

도구 결과는 Git 제외 `state/protected-deployment-20261012`의 단계별 JSON/로그, 서버 보호 경로의 배포/백업/수신/후보 검증 자료에 보존했다. 비밀 값과 민감한 본문은 공개 결과에서 제외했다.
