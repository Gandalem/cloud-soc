# 서버·애플리케이션·네트워크 통합 수집·분석 시나리오

## 목적과 데이터 흐름

이번 프로그래밍의 기본 목적은 서버 보안 로그 최소 3건, 애플리케이션 보안 관련 로그 최소 3건, 네트워크 트래픽 기록 최소 3건으로 총 9건 이상을 각각 수집·정규화·분석하는 것이다. 반복 공격 임계값 충족은 이 기본 목적의 필수 조건이 아니다. 세 종류의 개별 수집·분석과 세 종류 사이의 상관 경보는 별개이며, 상관 경보가 없어도 개별 기록을 조회·분석할 수 있어야 한다.

| 필수 입력 | 최소 기록 | 분석 내용 |
| --- | --- | --- |
| 서버 | Windows 또는 Linux 인증 성공·실패 3건 이상 | 시각·호스트·계정·출발지·인증 결과 |
| 애플리케이션 | 웹 HTTP 401 또는 403 접근 기록 3건 이상 | 시각·서비스·사이트·관측 출발지·응답 상태 |
| 네트워크 | 서로 다른 Flow ID의 Packetbeat 종료 Flow 3건 이상 | 시각·출발지·목적지·포트·프로토콜·흐름 ID 및 관측된 통신량 |

HTTP 인증·접근 거부 기록은 보안 관련 관측으로 사용하며 악성 요청으로 자동 판정하지 않는다. 네트워크는 로그 파일뿐 아니라 실제 통신에서 수집기가 생성한 흐름 메타데이터를 입력으로 사용한다.

서버의 인증 기록, 애플리케이션의 접근 기록, 네트워크 흐름을 중앙에서 정규화하고 조직·호스트·관측 출발지를 기준으로 시간상 연관된 활동을 경보로 연결한다. 원본은 기존 저장소에 보존하고 경보에는 원본 및 정규화 문서 참조와 단계별 증거를 연결한다.

```text
Windows Security ────────────┐
Linux SSH / journald ────────┼─ Filebeat / 기존 수집기 ──┐
Nginx / Apache / 앱 감사 ────┘                          │
                                                      ├─ 중앙 원본 인덱스
호스트 로컬 NIC ── Packetbeat (Flow / DNS / TLS) ───────┘
   → 기존 processing 워커 → soc-normalized-v1
   → 기존 detection 증분 워커 + 명시 선택 규칙
   → security-alerts → Portal 근거 조회 및 사건 조사
```

수집기는 [장치 설치](device_installation.md)와 [네트워크 수집](../deploy/agents/NETWORK.md)의 기존 설정을 사용한다. 웹 서버에 WAF를 자동 설치하지 않으며 패킷 본문을 추가로 저장하지 않는다.

## 수집 배치

| 환경 | 수집 대상 | 연결에 사용하는 필드 | 운영 조건 |
| --- | --- | --- | --- |
| Windows 서버 | Security 인증 성공·실패 | organization.id, host.id, source.ip, user.name | 감사 정책과 계정 권한 설정 필요 |
| Linux 서버 | SSH 인증 및 시스템 저널 | organization.id, host.id, source.ip, user.name | 기존 SSH 정규화 프로필 사용 |
| 웹 애플리케이션 | Nginx·Apache 접근 메타데이터 | 조직·호스트·출발지, service.name, HTTP 상태 | 사이트별 수집 경로 지정; 프록시 주소와 실제 사용자 구분 |
| 네트워크 | Packetbeat 종료 Flow·DNS·TLS | 조직·호스트·출발지, 목적지, flow_id | 이 시나리오는 대상 호스트 로컬 센서의 동일 host.id 사용 |

중앙 수집망 센서의 host.id가 대상 서버가 아닌 센서 자체를 가리킨다면 이번 호스트 상관 규칙에 그대로 연결하지 않는다. IP만으로 호스트 ID를 자동 추정하지 않는다. 조직 ID와 호스트 ID는 기존 등록 체계를 따르고 에이전트마다 임의로 다르게 부여하지 않는다.

## 시나리오 A: 웹 활동에서 호스트 인증으로

기본 3종 상관 규칙 `UNIFIED-THREE-SOURCE-001`은 애플리케이션 HTTP 401/403 1건 → 서버 인증 성공 또는 실패 1건 → 종료 네트워크 Flow 1건을 연결한다. 같은 조직·호스트·관측 출발지와 단계 순서를 요구하고, 단계 간 각각 300초, 전체 구간 900초로 제한한다. 세 입력이 각각 존재하더라도 순서·범위 조건이 다르면 이 상관 경보는 발생하지 않는다. 개별 수집·분석은 상관 조건과 독립적이다. 이 규칙은 저위험 활동 연관 관측이며 공격 탐지 확정이 아니다.

위 1건씩 연결 규칙은 보조 상관분석이며 각 환경 3건 요건을 충족했다는 판정에 사용하지 않는다. 아래 반복형 시나리오 A·B도 추가 분석이다.

### 기본 시나리오: 환경별 3건 이상 분석

다음 세 규칙을 함께 명시 선택한다. 각 규칙은 900초 구간을 사용하고 경보 재발행 억제도 900초로 둔다. 서버·네트워크는 같은 조직·호스트 범위, 앱은 같은 조직·호스트·서비스 범위에서 집계한다. 서로 다른 출발지 기록도 집계할 수 있다.

| 규칙 ID | 집계 대상 | 기준 |
| --- | --- | --- |
| UNIFIED-SERVER-MIN3-001 | 인증 성공 또는 실패 | 고유 서버 인증 관측 3건 이상 |
| UNIFIED-APP-MIN3-001 | HTTP 401 또는 403 | 고유 웹 관측 3건 이상 |
| UNIFIED-NET-MIN3-001 | 종료 Flow | 고유 관측 3건 이상이며 Flow ID도 3종 이상 |

서버·웹의 중복 관측 처리는 기존 cardinality 탐지기의 관측 식별을 재사용한다. 네트워크는 Flow 관련 필드로 중복 보고를 추가 제한한다. 기록을 복제해서 최소 수량을 채우지 않는다. 실제 수집 입력에서 관측되는 필수 메타데이터와 원본 참조를 분석 근거로 사용한다.

각 규칙은 독립적인 분석 결과를 만든다. 세 결과는 같은 조직·대상 호스트·운영자가 선택한 분석 구간으로 함께 해석해야 하며, 세 환경 모두 충족했다고 자동 판정하는 통합 완료 상태는 추가하지 않는다. 한 환경의 9건으로 다른 환경의 누락을 대신할 수 없다. 수집은 임계값에 도달해도 계속되며 3건은 수집 상한이 아니다.

규칙 `UNIFIED-WEB-HOST-001`은 같은 조직·호스트·관측 출발지에서 웹 HTTP 404가 5건 발생한 뒤, 마지막 웹 단계와 300초 이내에 서버 인증 성공이 나타나는 경우를 연결한다. 전체 보존 구간은 600초, 경보 재발행 억제는 600초다.

웹 단계는 서비스 이름이 존재하는 기록만 사용한다. 여러 사이트를 제공하는 같은 호스트의 웹 기록이 합쳐질 수 있으므로 경보 근거에서 실제 서비스와 사이트를 구분한다. 인증 주체가 웹 요청 주체와 같다는 의미는 아니다. 크롤러·관리자 접속·공유 NAT도 해당할 수 있다.

## 시나리오 B: 인증 실패·성공과 네트워크 흐름

규칙 `UNIFIED-HOST-NET-001`은 같은 조직·호스트·관측 출발지에서 동일 계정의 인증 실패 5건, 이후 300초 이내 인증 성공, 이후 300초 이내 종료 네트워크 Flow를 순서대로 연결한다. 전체 보존 구간은 900초, 경보 재발행 억제는 900초다.

실패와 성공은 계정 이름을 추가로 일치시킨다. Flow는 계정에 귀속시키지 않는다. 동일 source.ip 방향의 관측만 연결하며 반대 방향 트래픽을 자동으로 뒤집지 않는다. 종료 Flow의 시각은 최초 연결 시각이 아니고, 누적 바이트를 중간 보고마다 합산하지 않는다. 이 경보는 유출량·실행 프로세스·공격 성공을 판정하지 않는다.

## 프로그램 연결

규칙은 [unified_environment.yml](../rules/unified_environment.yml)에 작성하고 기존 고정 규칙 카탈로그에 등록한다. 기존 `ordered` 탐지기의 단계 매칭, 시간 구간, 조직 격리, 증거 참조 및 증분 워커의 체크포인트를 재사용한다. 일반 기본 워커에 자동 추가하지 않는다.

기존 normalizer가 `soc-normalized-v1`에 기록하도록 구성된 환경에서 별도 탐지 워커의 `--additional-rules`로 다음 두 ID를 선택한다. 기존 AUTH 워커의 상태 파일은 재사용하지 않는다. 신규 워커에 필요한 Elasticsearch 읽기·경보 쓰기 권한과 기존 중앙 설정이 준비되어 있어야 한다.

아래는 추후 사용자가 실행을 지시할 때 사용할 명령 형식이며 이번 작업에서 실행하지 않았다. 경로와 시작 시각은 환경에 맞게 지정한다. 시작 시각은 첫 실행 뒤 재시작에서도 유지한다.

```bash
PYTHONPATH=src python -m cloud_soc.detection \
  --run \
  --additional-rules UNIFIED-SERVER-MIN3-001,UNIFIED-APP-MIN3-001,UNIFIED-NET-MIN3-001,UNIFIED-THREE-SOURCE-001 \
  --state state/detection/unified-environment.sqlite \
  --start '<고정된 최초 정규화 시작 시각: ISO8601 및 시간대>' \
  --es-url 'https://<중앙 서버>:9200' \
  --ca-file '<신뢰할 CA 파일 경로>' \
  --api-key-file '<보호된 탐지 워커 키 파일 경로>'
```

위 명령은 실제 수신 데이터를 읽고 경보·상태를 기록하는 운영 명령이다. `--run`을 생략하면 기존 CLI가 설정 확인을 수행하므로, 현재 사용자의 모든 검증 금지 지시가 유지되는 동안에는 생략 형태도 실행하지 않는다. 파일에 명령을 적는 것과 실제 실행은 별개다.

## 장애·누락 해석

필수 조직·호스트·출발지·계정·증거 참조가 없으면 상관 성공으로 간주하지 않는다. 기록 부재와 경보 부재는 안전이나 수집 정상의 증거가 아니다. 시계 차이·지연 수신은 순서를 바꿀 수 있으며 기존 증분 워커의 지연 허용 범위를 벗어난 기록은 별도 정책 대상이다. 수집 상태는 Portal 수집 현황과 파이프라인 상태에서 운영자가 해석한다.
