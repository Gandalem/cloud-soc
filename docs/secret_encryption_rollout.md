# 암호화 강제 구현 및 운영 이관 상태

2026-11-02. 구현은 로컬 코드/격리 검증 단계다. 운영 키는 아직 이관하지 않았고 강제 모드를 활성화하지 않았다.

## 보호 계층 조사

현재 실행 호스트에서 /dev/tpm0, /dev/tpmrm0 없음, /sys/class/tpm 항목0, tpm2/vault 명령없음, 알려진 AWS/Vault/KMS 설정없음. 다른 서버/조직 계정에 서비스가 없다는 뜻은 아니다. 사용자도 서비스 유무를 모르는 상태다. 없는 KMS/Vault/TPM 대신 로컬 평문 마스터키를 생성하지 않았다. 신규 클라우드 자원·비용·IAM권한을 임의 생성하지 않았다.

## 구현

- cloud_soc.secret_store: 버전별 AES-256-GCM 암호문, 외부 KMS 데이터키 생성/래핑/복호화, 기대 KMS ARN 고정, 기관/용도/secret_id 인증 컨텍스트 및 AAD, 변조·기관교환 거부.
- 보호 계층 없이 암호문을 만들거나 해독할 수 없으며 로컬 마스터키 백엔드는 없다. KMS SDK는 기존 역할 기반 워크로드 자격증명만 허용한다. 정적 SDK 프로필/환경키는 KMS 부트스트랩으로 허용하지 않는다. Vault/TPM 실백엔드는 이번에 구현하지 않았다.
- SOC_SECRET_POLICY=required: 연결한 파일 읽기 경로의 평문 거부와 클라우드/ES의 직접 환경변수 인증정보 거부. 암호문 파싱/복호화 실패 시 평문으로 후퇴하지 않는다. SOC_SECRET_CONFIG_FILE은 비밀이 아닌 KMS/바인딩 정책 파일이다. 정책 파일도0600으로 보호한다.
- 연결된 읽기 경로: 공통 protected_key를 사용하는 AWS/정규화/탐지 CLI, Portal 조회 API키, multicloud ES클라이언트 및 Naver/Azure 비밀파일, 알림 워커, 정규화 진단도구. AWS 수집기는 강제 모드에서 역할 신원을 요구한다.
- 쓰기 경로: multicloud 정규화 신규키와 multicloud writer는 암호문 전용 write_new 사용. 중앙 워커/알림키 준비는 required 모드에서 암호문 기록, legacy 모드에서 기존 호환을 유지한다.
- 파일은0600/링크거부/크기상한/배타적 생성·fsync. 키 값이나 원문 오류를 출력하지 않는다. Python 메모리 완전삭제는 보장하지 않는다.

중요: 기존 운영을 갑자기 중단하지 않기 위해 미설정 정책은 legacy다. 따라서 이 코드만 배포해서 전체가 암호화 필수 상태가 되지는 않는다. `required` 프로필 전환 및 각 워크로드의 독립 정책/신원 배포가 필요하다. 서로 다른 워커가 모두 `/run/keys/worker.key`를 사용하므로 정책 파일은 서비스별로 분리해야 한다. 공통 정책 한 장으로 다른 워커의 키를 교환하도록 구성하면 안 된다.

Portal의 일반 계정 비밀번호 해시, Elasticsearch 부트스트랩 계정 암호, Slack 로컬 Fernet 마스터키, 기존 장치 등록 프로토콜은 이번 API키 이관의 자동 변환 대상이 아니다. 기존 Docker Env·과거백업·호스트진단 스크립트 등은 전체 배포 전 별도 인벤토리/정리해야 한다.

## 이관 도구

`python -m cloud_soc.secret_migrate`는 원본 평문 키파일을 유지하며 별도 암호문 파일을 만든다. source/destination 절대경로·보호권한·중복파일을 검사한다. --apply 없으면 KMS 호출/파일 쓰기 없이 계획만 검증한다. --apply 시 암호화 후 KMS 복호화와 원문 비교를 통과해야 파일을 배타적으로 생성한다. 원본/권한/키 만료/탐지 체크포인트를 자동 변경하지 않는다. 원본을 남기는 단계는 이관 준비일 뿐 평문 제거 완료가 아니다.

```text
python -m cloud_soc.secret_migrate --source <기존키 절대경로> --destination <새 암호문 절대경로> --config <0600정책파일> --binding-path /run/keys/worker.key
```

운영 보호 계층과 워크로드 신원을 준비하고 위 계획을 검토한 뒤에만 --apply를 사용한다. 이 예시를 placeholder 그대로 실행하지 않는다. config/examples/secret-policy.example.json은 형식 예시이며 실제 KMS키가 없어 실행 가능한 설정이 아니다.

## 남은 운영 작업

1. 실제 외부 KMS 또는 Vault/TPM을 선택/준비한다. 이번에 지원한 실백엔드는 AWS KMS이며 기존 ARN/역할이 필요하다. 서비스 존재를 추정해 신규 생성하지 않는다.
2. 운영자 권한으로 실제 키 목록·소유 서비스·파일/환경변수·백업 위치를 조사하고 기관별 정책과 워커별 독립 바인딩을 정한다.
3. 관리자 실행으로 검증된 암호문 사본 생성. 별도 워크로드별 정책·KMS권한·읽기전용 마운트·required 환경값을 기존 배포 계획/복구 계약에 반영한다. 현재 배포 관리자가 이 구성을 자동 배포하도록 완성된 상태는 아니다. 암호문 파일만 기존 경로에 덮어쓰지 않는다.
4. 격리된 연결 시험 후 서비스별 교체·실수집·정규화·탐지 인수. 기존 체크포인트를 유지한다. 복구 역시 암호문 참조 전환으로 준비한다.
5. 평문 env/파일/옛컨테이너/백업 사본은 인벤토리를 따라 정리하고 노출 가능 키는 순차 교체한다. 전체 미이관 키0·평문fallback0 확인 후에만 강제 전환 완료로 보고한다.

## 검증

합성 KMS/키로 암호문 비노출·nonce분리·기관/용도/ID교환·변조·KMS장애·평문/inline거부·누락정책·파일권한·이관계획 무쓰기·검증후복사·원본보존·덮어쓰기거부를 검사했다. 실제 KMS 연결·외부 키 이관·운영 배포는 미검증이다. 기존 처리/배포 권한·어댑터 등 관련106검사 및10subtests 통과. 보호 계층 없는 운영에 required를 무작정 켜면 작업이 중단되므로 자동 활성화하지 않았다.
