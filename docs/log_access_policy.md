# 조직별 로그 조회·보호된 원문 정책

2026-10-04 사용자 선택: **조직·역할·조회 사유·감사 기록을 확인한 뒤 허용된 원문 필드를 JSON으로 제공**한다. 전체 비마스킹 원문과 내보내기는 제공하지 않는다. 최초 로컬 구현 이후 지정 VMware 배포·실제 ES/API/Edge·조직/역할·감사 장애/복구·네 수집기 v3 수신 검증을 완료했다([후속 보고서](p2_source_access_validation_20261004.md)). 기존 메타데이터 실검증은 [별도 보고서](log_query_validation_20261004.md), 전체 상태는 [작업 목록](work_tracker.md)을 따른다.

## 권한과 제공 범위

| 역할 | 메타데이터 목록·상세 | 보호된 원문 필드 | 다른 기능 |
| --- | --- | --- | --- |
| 기존 admin | 기존 전체 조직 조회 유지 | 기능 활성화 및 `admin_source_organizations`에 명시한 조직만 | 기존 관리자 권한 유지 |
| viewer | 서버 설정에 명시된 조직만 | 차단 | 패키지·키·사건·운영 API 차단 |
| investigator | 서버 설정에 명시된 조직만 | 기능 활성화 시 같은 조직만 | 패키지·키·사건·운영 API 차단 |

역할과 조직은 읽기 전용 서버 설정으로 결정하며 브라우저 헤더·요청 JSON의 권한 주장은 받지 않는다. 목록에는 조직 필터를 강제하고 응답도 검사한다. 상세와 보호된 원문은 문서의 조직을 확인하며 타 조직·조직 누락은 문서 없음으로 응답한다. 페이지 커서는 계정·역할·조직에 묶인다. 조직 값은 에이전트가 제출한 메타데이터이므로 침해 호스트의 조직 위조까지 방지하는 신원 증명은 아니다.

허용 필드는 [조회 계약의 SOURCE_FIELDS](../src/cloud_soc/portal/log_contract.py)와 [해석 상세의 DETAIL_FIELDS](../src/cloud_soc/portal/security_detail.py)의 합집합이다. 시각·호스트·사용자·조직·IP·포트·승인된 Windows 감사/클라우드 메타데이터 등을 포함한다. 이름·경로·주소도 개인정보가 될 수 있어 조직과 목적 제한을 적용한다. 이를 익명화된 정보라고 주장하지 않는다.

ES에는 허용 필드만 요청한다. 메시지 본문, `event.original`, 명령 인자/명령줄, XML·스크립트 본문, 개인 키·비밀번호, 허용 목록 밖 필드는 반환하지 않는다. 허용 필드 안의 의심 문자열은 전체를 `[REDACTED]`로 가리고 예상하지 않은 객체는 `[WITHHELD]`로 대체한다. JSON 타입과 저장 시각을 유지하되 문자열 8,192자, 배열 64개, 전체 응답 64KiB 이내로 제한한다. 정규식은 완전한 DLP가 아니며 소스별 개인정보 검토가 필요하다.

이는 포털의 접근 제어다. ES/Kibana의 문서·필드별 권한을 도입한 것이 아니다. 직접 ES 계정이나 수집 키를 조회 사용자에게 주지 않는다. 2026-10-04 사용자 승인으로 과거 ES 문서는 삭제·재처리 없이 보존하고 일반 사용자는 보호된 허용 필드만 조회하며 ES/Kibana 직접 접근은 신뢰한 관리자에게 유지한다. 보존 기간·삭제·외부 백업 정책은 P2-02에서 별도 결정한다.

## 조회와 감사

`GET /api/logs/access`는 현재 계정의 기능과 조직 범위를 알려준다. 상세 화면에서 사용자가 사유를 선택하고 버튼을 눌러야 `POST /api/logs/source`를 호출한다. 요청 본문은 정확히 `index`, `id`, `purpose`만 허용한다. 사유는 `investigation`(조사), `receipt_validation`(수신 검증), `support`(지원) 중 하나이며 자유 텍스트는 받지 않는다. 기존 HTTPS 인증·Host/Origin·JSON·`X-Cloud-SOC: portal` 검사를 유지한다.

보호된 원문 처리기에 도달한 요청은 허용·권한 거부·문서 없음·잘못된 입력·조회 실패를 `SOC_STATE_DIR/log-access.sqlite`의 `source_access`에 기록한다. 저장 항목은 순번, UTC 시각, 계정, 역할, 사유 코드, 문서 참조의 SHA-256, 결과, 정책 버전이다. 문서 내용·비밀번호·헤더·원문 참조 자체는 저장하지 않는다. 해시는 익명화 보장이 아니다. 인증/CSRF/크기/쿼리 검사에서 처리기 진입 전에 거부된 요청은 이 테이블의 기록 대상이 아니다.

성공 감사가 커밋된 뒤에만 `audit_id`와 `protected-fields-v1` 응답을 반환한다. 감사 저장에 실패하면 503으로 조회를 차단한다. 화면은 JSON을 텍스트로 표시하고 저장소에 넣지 않으며 상세 닫기·페이지 이탈 시 지운다. 응답은 `no-store`다. 감사 DB는 서버 계정이 관리하는 로컬 파일이며 외부 서명·변조 방지 저장소·감사 조회 UI는 아직 없다. 감사 보존 기간과 자동 정리는 설정하지 않았다.

새 포털 이미지의 Gunicorn 접근 로그는 메서드·상태·처리 시간만 기록한다. URL/쿼리, Basic 사용자, Referer, 본문을 기록하지 않는다. 기존 실행 이미지와 과거 접근 로그는 이 변경만으로 갱신되지 않는다.

## 기본 차단과 선택적 배포 설정

기본 Compose에는 정책 파일을 연결하지 않는다. 이 경우 기존 관리자만 사용할 수 있고 보호된 원문은 차단된다. 정책을 연결하면 최대 20개 조회 계정, 계정당 최대 20개 명시 조직을 받는다. 와일드카드·빈 조직 목록·관리자 계정 재정의는 거부한다(`admin_source_organizations`는 빈 목록 허용). 설정 오류는 시작 시 실패하며 권한을 넓혀 대체하지 않는다.

정책 파일의 최소 예시는 다음과 같다. 비밀번호를 넣지 않는다.

```json
{
  "version": 1,
  "protected_source_enabled": false,
  "admin_source_organizations": [],
  "users": []
}
```

시험 조직을 검증한 뒤 `protected_source_enabled`를 `true`로 하고 관리자 허용 조직을 명시한다. 조회 계정 항목은 `username`, `password_hash`, `role`(`viewer` 또는 `investigator`), `organizations` 배열의 네 필드로 구성한다. `password_hash`에는 Werkzeug `generate_password_hash()` 기본 scrypt로 생성한 해시를 넣는다. 비밀번호는 숨김 입력으로 받고 명령 인자·셸 이력·Git에 기록하지 않는다. 파일 자체도 해시가 포함된 비밀 설정이므로 Git 밖 보호 경로에 둔다. 예시의 조직/계정을 실제 설정으로 간주하지 않는다.

Linux 파일은 일반 파일·32KiB 이하·다른 사용자 읽기 권한 없음이어야 한다. 예: 신뢰한 root 소유, 그룹 1000, 파일 0640, 부모 디렉터리 0750. UID 1000 포털의 읽기 접근을 확인한다. 정책 파일·부모 디렉터리를 비신뢰 사용자에게 쓰기 허용하지 않는다. Windows에서는 보호된 NTFS ACL을 별도로 준비한다.

[선택적 Compose 설정](../deploy/server/compose.log-access.yaml)은 호스트 파일을 읽기 전용으로 연결한다. 다음 명령은 **보호 백업·이전 이미지 보존과 검토한 소스 전달 후 수행할 후속 배포 절차**이며 이번 로컬 검증에서는 실행하지 않았다.

```bash
export SOC_LOG_ACCESS_POLICY_FILE_HOST=/absolute/protected/path/log-access-policy.json
docker compose --env-file state/server/compose.env \
  -f deploy/server/compose.yaml -f deploy/server/compose.log-access.yaml \
  up -d --no-deps --build portal
```

기존 설치기를 재실행하거나 ES 권한을 넓힐 필요는 없다. 정책 변경은 포털 재기동 시 적용한다. 계정별 시험은 인증 캐시가 섞이지 않는 별도 브라우저 세션에서 수행한다. 컨테이너 import·UID·파일 판독·배포 해시와 기존 DB 행/BLOB 보존을 실제로 확인해야 배포 완료로 기록한다.

이번 VMware 검증은 보호된 `state/p2-20261004-5c79b99/release`의 소스와 `compose.portal.yaml` 이미지/빌드 경로 재정의를 사용했다. 서버의 기존 Git checkout은 갱신하지 않았으므로 그 checkout에서 기본 `--build`만 실행하면 이번 배포 소스가 재현되지 않는다. 다음 Git 배포는 이번 변경의 반영과 검토한 소스/이미지 해시 대조 후 진행한다. 해당 환경의 정확한 실행 이미지·정책/백업 위치는 후속 보고서를 따른다.

## 마스킹·백업과 남은 검증

새 `privacy.js`의 `privacy_policy=v3`는 비밀 명령 옵션, 일반 URI의 자격 증명·쿼리/fragment, 숨김 제어 문자를 추가로 가린다. 포털 표시에도 같은 문자열 보호를 적용한다. 이미 설치된 v2 에이전트·기존 ZIP·미전송 큐·기존 ES 문서는 자동 갱신하지 않는다. 실행 중 설치에 신규 설치기를 덮어쓰지 않는다. 안전한 정책 갱신과 실제 v3 수신 검증은 별도 단계다([수집 보호 가이드](collection_protection.md)).

새 포털은 기능 차단 상태에서도 감사 DB를 초기화한다. 새 백업 도구는 감사 DB가 있으면 format 2로 포함하고 기존 format 1 백업의 verify/격리 restore도 유지한다. 정책 파일·계정 해시는 DB 백업 대상 밖이므로 별도 보호 보관한다. 이전 도구는 새 감사 DB를 포함하지 않으므로 배포 버전과 맞는 도구를 사용한다([백업 안내](portal_backup.md)).

최초 로컬 검증 뒤 남았던 지정 VMware 배포·실제 로그/네트워크 ES 허용 필드→API→브라우저 JSON, 조직별 허용/거부·사유/감사 참조 해시를 후속 검증했다. 실제 소스 검토에서 Ubuntu 프로비저닝 자료를 제외했고 기존 큐/키/ID 보존형 v3 교체와 실제 민감 표식 차단도 확인했다. 실제 감사 34개 행의 format 2 백업·격리 복원이 일치했다. 임시 조회 계정 3개는 제거/이전 자격 증명 401을 확인했으며 최종 정책은 `users=[]`, 관리자 보호 조회 조직 `vmware-lab`이다. 새 영구 조회 계정은 승인된 조직/역할로 별도 구성한다. AWS 운영 배포·ES DLS·전체 원문 제공·외부 변조 방지 감사·ES 스냅샷·보존 정책은 이 결과로 추정하지 않는다.
