# 단일 설치 토큰과 자동 중앙 수신 확인 (P0C-03)

## 현재 지원 범위

**기본 비활성화이며 관리자가 명시적으로 활성화합니다.** 2026-10-04 지정 VMware 시험 서버에서 Windows·Ubuntu의 로그 전용/통합 설치, 실제 중앙 수신, 수신 서버 중단과 보존형 새 토큰 재등록, 만료·경합·최소 권한·정리 서비스 및 실제 브라우저를 검증했습니다. [검증 결과와 제한](p0c03_validation_20261004.md), [작업 기록](work_tracker.md)을 참조하세요. 기존 운영 서버로 자동 배포하지 않습니다.

- 새로 생성한 **Windows·Ubuntu의 로그 전용 또는 로그+네트워크 패키지**를 지원합니다. 기존 ZIP은 자동 갱신되지 않습니다.
- 수동 키 경로도 유지하며 로그 전용에는 host 키 하나만 발급합니다.
- `-Repair`, `-ResumeRepair`, `-UpdateDiscovery`에 토큰을 사용하지 않습니다. 기존 키·큐를 자동 교체하지 않습니다.
- 기존 서비스가 있으면 신규 토큰 설치가 차단됩니다. 확인된 실패 Enrollment만 명시적 새 토큰 재등록을 허용합니다. 정상·수동·출처 불명 설치는 채택하지 않습니다.

## 사용 흐름

1. 중앙 서버를 준비한 후 필요한 OS와 로그/네트워크 범위의 새 패키지를 만듭니다.
2. ZIP 또는 tar.gz를 내려받아 포털의 SHA-256과 대조한 뒤 전체 파일을 압축 해제합니다.
3. 해당 패키지의 **설치 토큰**에서 대상 별칭과 수집 키 유효 기간을 선택합니다. 시험은 1일을 권장합니다.
4. Windows는 관리자 PowerShell에서 `install.ps1 -Enroll -PackageSha256 ...`, Ubuntu는 `sudo bash install.sh --enroll --package-sha256 ...`을 실행합니다. 네트워크 포함 Ubuntu는 `--interface ens33`처럼 실제 NIC를 지정하고 Windows는 필요 시 `-InterfaceGuid`를 지정합니다. 해시는 공개 아카이브 해시입니다.
5. 설치 경로·중앙 TLS 및 필요한 NIC/Npcap 검사를 통과한 뒤 숨김 입력 창에 토큰 **하나**를 붙여 넣습니다. 역할 키를 직접 복사하지 않습니다. Ubuntu는 Python 3·OpenSSL·systemd가 필요합니다.
6. 각 키가 해당 Beat의 keystore에 표준 입력으로 저장됩니다. 모든 필요한 수집기의 설정·출력 검증을 마친 뒤 서비스와 Discovery를 시작합니다. Windows Discovery는 SYSTEM 독립 실행 파일이고 Ubuntu는 systemd timer입니다.
7. Filebeat에 민감정보 없는 합성 검증 이벤트 한 건을 제공합니다. 네트워크 포함이면 이미 설정된 Elasticsearch 수신 주소로 TCP 연결을 한 번 생성합니다. 검증 파일은 기본 fingerprint 대기 기준을 넘도록 약 1.3KiB의 무의미한 채움 문자열을 포함합니다. Packetbeat는 승인된 NIC의 흐름 메타데이터만 수집합니다.
8. 중앙 서버가 고유 표식·조직·패키지·인증 키·수집기 ID·서버 수신 시각이 일치하는 로그와, 네트워크 포함이면 TCP 흐름 문서까지 조회해야 완료합니다. 설치기가 Elasticsearch에 직접 쓰는 대체 검증은 하지 않습니다.

토큰은 명령줄·스크립트·ZIP·파일에 넣지 마세요. 포털에 한 번 표시하며 창을 닫으면 화면 값이 지워집니다. 복사한 클립보드는 사용 후 다른 비민감 값으로 교체하세요. 엄격 검사가 기본이며 인증서·이름·유효기간·폐기 정보 검증 실패를 먼저 해결합니다. Ubuntu 토큰 경로는 같은 서버의 서명된 CRL 배포점을 요구하고 폐기 검사를 완화하는 옵션을 제공하지 않습니다. Windows의 기존 명시적 예외 옵션은 기본이 아니며 이번 시험에서 사용하지 않았습니다. 토큰 기능이 인증서·실행 정책·Npcap 요구 사항을 우회하지 않습니다.

## 서버 준비 (관리자용)

기존 데이터·CA·패키지·키 이력을 백업하고 복원 검증한 뒤 수행합니다. 새 DB 백업 도구는 Enrollment 테이블과 과거 스키마 모두 지원하며 암호화된 응답도 함께 보존합니다. 복원은 기존 절차처럼 별도 위치에서만 시험하고 운영 DB를 덮어쓰지 않습니다.

1. 검토한 코드를 반영하고 새 의존성을 포함한 `bootstrap`, `portal`, `enrollment-cleanup` 이미지를 빌드합니다.
2. `bootstrap`을 명시적으로 실행해 기존 수신 final pipeline과 매핑을 준비합니다. 기존 문서는 재작성하지 않습니다. 충돌 매핑이 있으면 중단하므로 먼저 검토하세요.
3. 중앙 Compose 환경에 `SOC_ENROLLMENT_ENABLED=1`을 설정합니다. **`enrollment` 프로필의 정리 서비스도 반드시 함께 실행**합니다. 기본값 `0`은 토큰 발급·설치 API를 막습니다.
4. 정리 서비스의 동작과 중단된 시험 세션의 키 폐기를 확인한 후 기능을 시험하세요. 서비스가 내려가면 키 폐기 재시도가 진행되지 않습니다.

기존 서버 상태와 현재 실행 소스의 반영 방식에 맞춰 관리자가 아래 구조를 사용합니다. 이것만 실행한다고 배포·검증이 완료되는 것은 아닙니다.

```bash
sudo docker compose --env-file state/server/compose.env \
  -f deploy/server/compose.yaml --profile enrollment \
  build bootstrap portal enrollment-cleanup

# 사전에 최신 백업 검증 및 변경 범위 확인
sudo docker compose --env-file state/server/compose.env \
  -f deploy/server/compose.yaml run --rm bootstrap

# SOC_ENROLLMENT_ENABLED=1 설정 후
sudo docker compose --env-file state/server/compose.env \
  -f deploy/server/compose.yaml --profile enrollment \
  up -d --no-deps portal enrollment-cleanup
```

정리 서비스는 관리자 비밀번호·조회 계정 없이 발급 계정과 CA만 사용합니다. 매분 만료된 미완료 세션과 폐기 대기 키를 처리합니다. 완료한 설치의 유효 키는 폐기하지 않습니다. 비활성화할 때도 미완료 세션의 취소·폐기를 먼저 확인하고 정리 서비스를 중지하세요. 포털 컨테이너의 내부 HTTP 포트를 직접 공개하지 않고 TLS 게이트웨이만 노출해야 합니다.

## 실패·재시도

- **토큰 만료:** 발급 후 15분 이내 최초 사용해야 합니다. 사용 전 만료에는 발급된 키가 없습니다.
- **응답 유실:** 같은 설치 프로세스가 같은 고유 시도 비밀로 최대 3회 재시도합니다. 새로운 키를 만들지 않고 기존 암호화 응답을 전달합니다. 다른 프로세스의 시도는 거부합니다.
- **설치 프로세스 종료 / 토큰 분실:** 시도 비밀은 디스크에 저장하지 않으므로 다음 프로세스에서 채택하지 않습니다. 포털 이력에서 취소·키 폐기를 먼저 확인하고 새 토큰을 준비하세요. 기존 설치 흔적이 있으면 복구 절차가 먼저입니다.
- **부분 발급 / 발급 프로세스 종료:** 패키지·세션·역할에 묶인 고정 키 이름으로 폐기합니다. 폐기를 확인하지 못하면 `키 폐기 확인 필요`로 남기고 정리 서비스가 재시도합니다. 새 토큰으로 기존 키를 무작정 덮어쓰지 않습니다.
- **중앙 미수신:** 설치기의 대기 창은 약 3분이며 개별 통신에도 시간 제한이 있습니다. 미수신이면 성공을 출력하지 않습니다. 시작한 소유 서비스는 중지·비활성화하고 큐·키 저장소·복구 기록을 보존합니다. 실패한 설치 키는 폐기하므로 정상 Repair만으로 키 인증이 복구되는 것은 아닙니다. 아래의 명시적 재등록을 사용합니다.
- **방치 세션:** 키 전달 후 30분 안에 수신 확인이 끝나야 합니다. 만료되면 미완료 키를 폐기하며 중앙 연결 장애 시 폐기 대기로 남습니다. 정리 지연 동안 키는 실제 발급 만료일까지 유효할 수 있으므로 정리 서비스 장애를 운영자가 확인해야 합니다.
- **수신 확인 완료:** 과거 설치 검증 결과입니다. 현재 접속 상태·무손실·모든 로그 수집을 뜻하지 않습니다. 이후 키 중지는 기존 발급 키 관리에서 처리합니다.

## 확인된 실패 설치의 새 토큰 재등록

서버·조직·OS·수집 범위·CA와 보호 기록/파일 해시가 같은 실패 설치만 대상입니다. 서비스·Discovery와 수집기 프로세스를 중지한 상태에서 새 전체 패키지의 무결성을 확인하세요. 정상 완료 설치, 수동 설치, 변경된 NIC/설정/키·알 수 없는 상태는 자동 채택하지 않습니다.

```powershell
# Windows: 새 공개 ZIP 해시, 토큰은 실행 후 숨김 입력
.\install.ps1 -Enroll -ReEnroll -PackageSha256 '<SHA256>' -DryRun
.\install.ps1 -Enroll -ReEnroll -PackageSha256 '<SHA256>'
```

```bash
# Ubuntu: 네트워크 포함이면 같은 기존 NIC를 지정
sudo bash install.sh --enroll --reenroll --package-sha256 '<SHA256>' --dry-run
sudo bash install.sh --enroll --reenroll --package-sha256 '<SHA256>'
```

DryRun은 토큰/키 발급, 네트워크 요청, 파일/서비스 변경을 하지 않습니다. 실제 재등록은 중앙의 이전 실패 키 폐기를 재확인한 뒤 새 세션의 역할 키를 전달합니다. 준비 중 실패는 검증한 소유 디렉터리와 기록을 보호 보관한 뒤 다시 준비합니다. 시작 후 실패는 전체 파일 백업을 검증하고 같은 수집기 ID·큐·registry를 유지합니다. 큐를 이전 백업으로 되감거나 초기화하지 않으며 새 합성 이벤트의 실제 중앙 수신까지 확인해야 완료합니다.

강제 종료로 키/설정 교체 중 파일 해시나 보호 기록이 불일치하면 자동 복구하지 않습니다. 상태와 백업을 보존해 검토하세요. 모든 정전 시점의 자동 재개·서버/CA 이행·Beat 바이너리 업그레이드는 지원하지 않습니다. Windows 로그 전용 재등록 중 Repair 자체가 중단된 상태의 `-ResumeRepair`는 지원하지 않습니다.

## 보안·검증 계약

- 토큰과 시도 비밀은 각각 256비트 난수입니다. DB에는 각각의 SHA-256만 저장합니다.
- 재전달 응답은 클라이언트 시도 비밀에서 유도한 Fernet 키로 암호화합니다. 서버에 별도 복호화 비밀을 저장하지 않으며 완료·취소 시 응답을 비웁니다. 프로세스 메모리에는 통신·keystore 전달에 필요한 비밀이 일시적으로 존재합니다.
- SQLite 원자적 예약 후 키를 발급합니다. 예약 중 중단된 세션은 자동 재발급하지 않습니다. 오래된 DB 복원으로 동일 이름의 원격 키가 있으면 중복 발급을 거부합니다.
- host/network 키는 역할을 분리하고 해당 Windows 또는 Linux 수집 인덱스에 `create_doc`·`auto_configure`만 허용합니다. 읽기·삭제·키 관리 권한은 없습니다. Beat 연결 검사에 필요한 `monitor`, Packetbeat의 기존 파이프라인 읽기만 추가합니다.
- 수신 final pipeline이 클라이언트가 보낸 검증 신원 필드를 제거하고 실제 API 키 메타데이터에서 다시 생성합니다. Enrollment 키의 조직도 중앙 메타데이터로 고정합니다. 인증 키 메타데이터가 없는 기존 키는 이 검증에 사용할 수 없습니다.
- 수신 API는 원문을 반환하지 않으며 부분 샤드 실패·조회 시간 초과·누락/다른 final pipeline을 성공으로 처리하지 않습니다. host는 합성 검증 행위, network는 같은 고유 표식을 가진 TCP 흐름 문서를 요구합니다. 정확한 TCP 5-tuple 대조나 장치 원격 attestation은 아닙니다.
- 설치 API 3개만 토큰 인증을 사용합니다. 다른 관리자 화면·API는 기존 Basic 인증과 CSRF를 유지합니다. 브라우저 요청·리다이렉트·비 HTTPS·과대 요청/응답을 거부합니다. 인증 헤더·요청/응답 본문을 로그에 추가하지 마세요.
- 실제 배포 전에는 Elasticsearch 9.5.2의 인증 메타데이터 파이프라인, 역할 권한, 양 수집기의 새 표식 매핑과 서비스 상태를 별도로 검증해야 합니다. 모의 테스트로 이 결과를 대신하지 않습니다.

참고: [Elastic 인증 사용자 processor](https://www.elastic.co/docs/reference/ingest-processor/ingest-node-set-security-user-processor), [Packetbeat 흐름 문서](https://www.elastic.co/docs/reference/beats/packetbeat/configuration-flows).
