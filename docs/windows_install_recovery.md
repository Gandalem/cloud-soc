# Windows 설치와 안전한 복구

2026-10-01 실제 시험 VM 후속: 통합 설치와 `-Repair`, 전송 장애의 보호 롤백, 강제 종료 후 `-Repair -ResumeRepair` 및 대기 데이터 중앙 도착, 재부팅 후 자동 시작과 새 로그/통신 수신까지 검증했습니다. SYSTEM 대기는 실행 전 `LastRunTime` 대비 새 실행 여부와 단조 시간 제한을 사용하고 새 보고서 검사도 유지합니다. 공통 TLS 도구를 명시 로드해 복구에서 `Get-SystemCurl` 누락으로 중단되는 문제를 고쳤습니다. 수정은 **새 패키지**에 적용되며 기존 ZIP을 바꾸거나 유효한 동일 조직의 기존 키를 재발급할 필요는 없습니다. 검증 결과와 한계는 [작업 기록](work_tracker.md)을 참고하세요. 전체 Windows 버전/조직 GPO와 모든 정전 시점의 인증을 의미하지 않습니다.

2026-10-01 IP 주소 TLS 호환 보완: 일부 Windows curl/Schannel은 올바른 IP SAN과 `--cacert` 조합도 이름 불일치로 거부합니다. IPv4 주소에서 curl 인증서 오류가 발생하면 번들의 `tls-probe.cs`로 해당 연결만 다시 검증합니다. Windows 기본 IP/DNS 이름 검사, 번들 CA와 최종 루트 인증서의 바이트 일치, 전체 체인/유효기간/서버 인증 용도 및 온라인 폐기 검사를 유지합니다. 폐기 정보 조회 불가 허용은 기존 명시적 `-AllowUnavailableRevocation`에만 적용되며 알려진 폐기나 다른 체인 오류를 허용하지 않습니다. OS 신뢰 저장소·다운로드 검증·에이전트 TLS full 설정은 변경하지 않습니다. 이 파일이 포함된 새 패키지가 필요하며 기존 ZIP 파일을 수동 수정하지 마세요.

2026-09-23 요청에 따른 **신규 설치 준비 단계 개선**입니다. 현재 구현을 Enrollment 기반 완성형 배포 제품이나 전체 자동 복구로 보지 않습니다. 기존 설치·큐·키를 보존하는 원칙은 유지합니다.

2026-09-28 후속 변경: SYSTEM `Restricted`와 기존 PowerShell Discovery의 비호환을 해소하기 위해 주기적 작업을 독립 .NET 실행 프로그램으로 전환합니다. 실행 정책은 변경하지 않습니다. 아래 초기 적용 설명보다 [현재 실행 방식과 진단](windows_native_discovery.md)을 우선 적용합니다. 관리자 설치 진입점의 PowerShell 정책과 앱 제어 정책은 계속 존중합니다.

## 변경된 흐름

2026-09-30 P0C-02 1차 후속: **새 Windows 네트워크 포함 패키지**는 `bundle-windows.ps1`의 통합 준비/commit을 사용합니다. 아래 단독 설치기 설명은 로그 전용 설치와 이전 ZIP의 흐름이며, 기존 ZIP/실행 중 PC는 자동 변경되지 않습니다. VMware 포털과 새 ZIP에 반영하고 기존 자료 보존·실제 HTTPS 다운로드/내부 Git 소스 해시를 검증했습니다. 실제 PC 통합 설치/Packetbeat 캡처·중앙 네트워크 수신은 아직 수행하지 않았습니다. 기존 수집 PC는 로그 전용 갱신 ZIP의 `-UpdateDiscovery`를 사용하며 신규 통합 설치를 다시 실행하지 않습니다.

- 두 수집기의 기존 상태·호스트 소스·OS/관리자/Npcap/NIC/TLS 사전 검사를 먼저 수행합니다.
- Filebeat SYSTEM 검사·다운로드·설정/호스트 키 인증과 Packetbeat 다운로드·설정/네트워크 키 인증을 각각 보호 staging에서 끝냅니다. 키는 ZIP·receipt·인자에 평문으로 넣지 않습니다.
- 소유 토큰과 전체 준비 파일 SHA256·ACL/링크를 대조한 뒤 두 경로를 승격하고, 최종 설정/연결 검사도 모두 끝내야 서비스를 등록합니다. Discovery 작업은 두 서비스가 안정적으로 시작된 후에만 반복 실행을 설정합니다.
- 시작 시도 전 실패는 소유 자원만 정리합니다. 시작을 한 번이라도 시도한 뒤에는 소유 서비스만 중지/비활성화하고 큐·키·보호 receipt를 보존합니다. 데이터가 이미 발생했을 수 있으므로 파일을 과거 상태로 되감거나 지우지 않습니다.
- 보호된 `bundle-pending.json`과 단계 journal이 중단 흔적/정리 실패의 무분별한 재설치를 차단합니다. 2026-10-01 로컬 수정본은 신원이 확인된 **중지된 두 서비스**를 명시적 `-Repair`로 복구합니다. 새 보호 복구 기록까지 일치하는 시작 후 실패 상태만 재시도를 지원하며, 자동 재개나 구버전 중단 상태의 무조건 채택은 하지 않습니다. 파일/receipt를 삭제해 우회하지 마세요. Filebeat만 있는 설치는 아래 로그 전용 복구 경로를 사용합니다.

통합 작업에도 파일 이동 두 번과 서비스 시작 두 번이 있으므로 운영체제 수준의 완전한 원자성은 아닙니다. 정상 예외는 소유권 확인 후 보상 정리하고, 정전/강제 종료에는 보존·차단합니다. 서비스 Running/인증 성공만으로 중앙 문서 수신을 SUCCESS로 표시하지 않습니다. Linux 네트워크 설치는 아직 순차 흐름입니다.

1. Windows x64·관리자·기존 서비스/경로 충돌·CA 파일을 확인합니다. 중앙 HTTPS에 제한 시간 20초의 자격 증명 없는 요청을 보내 CA/TLS·연결을 확인합니다. 이 단계는 API 키 권한이나 로그 쓰기 성공을 증명하지 않습니다.
2. 네트워크 묶음은 Filebeat 설치 전에 Npcap·활성 NIC·중앙 TLS를 먼저 확인합니다. NIC 미지정 시 기본 IPv4 경로가 있는 활성 물리 NIC를 표시합니다. 한 개여도 `y/yes` 확인이 필요하고, 여러 개면 번호를 선택합니다. 기본은 취소입니다. VPN/가상 NIC는 기존 `-InterfaceGuid`를 명시합니다.
3. `%ProgramData%\Cloud-SOC\staging\<random>`을 SYSTEM/Administrators 전용 ACL로 생성합니다. 기존 staging 부모의 권한이 예상과 다르면 덮어쓰지 않고 중단합니다.
4. Filebeat는 다운로드 전에 **일회성 SYSTEM Discovery 예약작업**을 실행합니다. 작업 종료 코드뿐 아니라 해당 실행의 새 `discovery-report.json` 생성 시각도 확인하고 임시 작업을 제거합니다. `Running/Queued` 상태를 완료로 간주하지 않습니다.
5. staging에서 고정 SHA-512 검증, 압축 해제, keystore 입력, `test config`와 `test output`을 수행합니다. 실패하면 이번 실행의 소유 토큰과 정확한 경로를 검사한 뒤 해당 디렉터리만 정리합니다.
6. 준비 완료 후에만 최종 Program Files 경로로 이동합니다. staging의 절대 경로를 최종 경로로 재생성하고 설정/연결 검사를 반복합니다. 디렉터리 이동은 동일 볼륨을 전제로 하며, 다른 볼륨이면 안전하게 실패합니다.
7. Filebeat의 영구 SYSTEM Discovery 작업을 다시 검사한 뒤 서비스를 생성·시작합니다. Packetbeat도 staging 검증 후 별도로 서비스를 생성합니다.

SYSTEM 작업은 임시 스크립트·설정·예약작업 없이는 검증할 수 없습니다. 따라서 사전 단계의 계약은 **'파일이 전혀 생기지 않음'이 아니라 '영구 수집 서비스를 만들기 전에 검사하고 소유 임시 자원을 정리함'**입니다. 보호된 공용 staging 부모 디렉터리는 남을 수 있습니다.

SYSTEM과 대화형 사용자의 환경은 다릅니다. 작업 디렉터리와 Discovery 루트를 명시했지만, 사용자가 보고한 `LastTaskResult=1`의 정확한 원인을 확인한 것은 아닙니다. [Microsoft 작업 액션 문서](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/new-scheduledtaskaction?view=windowsserver2025-ps)에 따라 `WorkingDirectory`를 지정하며 PowerShell 실행 정책이나 인증서 검증은 우회하지 않습니다. AllSigned/GPO 환경은 보조 스크립트까지 승인된 서명이 필요합니다.

| 실패 지점 | 동작 |
| --- | --- |
| OS/관리자/NIC/Npcap/TLS 사전 검사 | 수집 서비스와 설치 디렉터리를 만들지 않고 중단 |
| SYSTEM Discovery/다운로드/체크섬/키·설정 검사 | 임시 작업 종료·해제 후 이번 실행의 staging 정리 |

| 임시 작업 종료/해제 실패, 경로 링크/소유권 불일치 | 실행 중 작업이나 다른 파일을 지우지 않도록 보호 상태 유지 |
| 서비스 시작 시도 후 실패 | 서비스 중지/비활성화, 큐·registry·keystore 보존. 자동 삭제하지 않음 |
| 기존/구버전 부분 설치 발견 | 기존 상태를 바꾸지 않음. 새 staging 롤백이 과거 설치까지 정리하지 않음 |

오류 시 종료 코드는 1입니다. 모르는 디렉터리·junction·reparse point를 따라 재귀 삭제하지 않습니다. 강제 프로세스 종료·정전까지 자동 복구하는 영속 트랜잭션은 아직 아니며, 정리 실패 경로도 무조건 재사용하지 않습니다.

## 적용 방법

중앙 포털에 변경 코드가 반영된 후 **새 설치 패키지를 생성**해야 합니다. 기존 SQLite의 ZIP은 자동 업데이트하지 않습니다. `transaction-windows.ps1`을 포함한 패키지 전체를 사용합니다. 설치 스크립트 한 파일만 기존 설치 폴더에 덮어쓰지 마세요.

네트워크 묶음의 새 기본 명령:

```powershell
# 새 패키지를 해시 확인 후 압축 해제한 관리자 PowerShell에서 실행
.\install.ps1
# NIC/파일을 탐색하거나 설치하지 않는 설정 미리보기
.\install.ps1 -DryRun
```

`-DryRun`에서 NIC를 생략하면 합성 GUID로 미리보기만 출력합니다. 실제 NIC 선택·SYSTEM 테스트·TLS·키 인증을 통과했다는 의미가 아닙니다. 키는 기존처럼 호스트용/네트워크용을 각 Beat keystore에 입력합니다. 읽기 권한을 수집 키에 추가하지 않습니다.

## Schannel: the revocation status is unknown

Windows curl의 엄격한 인증서 폐기 확인이 실패한 상태입니다. 현재 실습 CA 생성기는 CRL/OCSP 배포점을 제공하지 않으므로 서명·주소·기간이 맞아도 이 단계에서 중단될 수 있습니다. 에러 60은 다른 인증서 오류에도 사용하므로 코드만 보고 자동 우회하지 않습니다. 이 사전 검사는 키 입력/서비스 설치 전이며, 이번 실패를 이유로 기존 설치나 폴더를 삭제하지 마세요.

원칙적으로 운영 환경은 조회 가능한 폐기 정보가 있는 인증서를 사용하고, 기업 CA라면 CRL/OCSP 연결 문제부터 해결합니다. 관리자가 신뢰 경로를 확인한 사설 실습 CA에 한해 **새 버전 패키지**에서 다음 선택 옵션을 사용할 수 있습니다.

```powershell
# 승인된 사설 CA에서 폐기 정보 조회 불가를 허용할 때만 사용
.\install.ps1 -AllowUnavailableRevocation
```

이 옵션은 중앙 서버의 인증정보 없는 사전 검사에만 curl `--ssl-revoke-best-effort`를 적용합니다. 기본값은 계속 엄격 검사입니다. CA 서명·서버 이름/IP·유효기간과 확인된 폐기 여부는 계속 검증하지만, 폐기 정보가 없거나 조회 서버가 오프라인인 경우에는 폐기 사실을 확인하지 못한 인증서도 허용될 수 있습니다. 인증서가 만료되었거나 다른 서버용이면 이 옵션으로 해결하지 않습니다.

Windows 신뢰 저장소/전역 폐기 설정, 공식 Elastic 다운로드, Beat 설정과 인증 경로는 변경하지 않습니다. `--insecure`, `-k`, `--ssl-no-revoke`는 사용하지 않습니다. [curl 공식 옵션 설명](https://curl.se/docs/manpage.html#--ssl-revoke-best-effort)을 참고하세요.

기존 ZIP은 변경되지 않으므로 중앙 포털에 수정 코드를 반영한 뒤 다른 이름으로 **새 패키지를 생성·다운로드·해시 확인·새 폴더에 압축 해제**해야 합니다. 예전 `1234-setup.zip`에 이 옵션을 입력해도 지원되지 않습니다. 기존 패키지의 일부 파일을 수동으로 바꾸면 원래 SHA256SUMS와 달라집니다. TLS 검사 통과 후에도 관리자/Npcap/SYSTEM·키 인증·실제 수신을 따로 검증해야 합니다.

## 기존 Filebeat를 발견한 경우

2026-09-28 추가한 복구 경로는 **중지된 Filebeat 9.5.2 서비스가 있고 Discovery 예약작업이 없거나, 동일 설치의 비활성 작업만 남은 설치**를 대상으로 합니다. 현재 보고된 부분 설치를 위한 제한된 복구이며 모든 잔존 상태를 삭제하는 재설치 기능이 아닙니다.

새 패키지의 `install.ps1`은 기존 Filebeat를 발견하면 복구 가능 여부를 검사하고 `Back up and recover ... [y/N]`을 표시합니다. 사용자는 복구에 동의하면 되며 서비스/예약작업을 직접 등록할 필요가 없습니다. 자동화 환경에서는 `-Repair`로 이 복구에 명시적으로 동의할 수 있습니다. `-DryRun`은 복구하지 않습니다. 사설 CA의 폐기 정보 조회 불가 허용은 여전히 별도의 `-AllowUnavailableRevocation` 선택입니다.

복구기는 다음을 순서대로 수행합니다.

1. 기존 서비스 경로·SYSTEM 계정·중지 상태, endpoint/조직/CA/keystore 설정 일치, 보호 ACL·링크 없음, 보관된 공식 ZIP의 고정 SHA-512와 설치된 배포 파일의 일치를 검사합니다. 기존 Discovery는 루트 경로의 단일 SYSTEM/Highest 작업, 정확한 PowerShell/스크립트 경로와 지원 인자, Disabled 상태일 때만 허용합니다. 다른 서버/조직으로의 이전, 사용자 변경 배포 파일, 실행 중 서비스 및 활성/출처 불명 작업은 자동 덮어쓰지 않습니다.
2. 동의 후 `%ProgramData%\Cloud-SOC\recovery\<random>`에 관리자/SYSTEM 전용 전체 파일 백업을 만들고 원본/복사본 해시를 대조합니다. 백업 용량 외 256 MiB 여유 공간을 요구하며 실패한 백업도 임의 삭제하지 않습니다. 백업에는 키 저장소/큐가 포함되므로 외부에 공유하지 마세요.
3. 새 패키지의 Discovery 스크립트를 적용하되 기존 설정·수집 정책·조직·키·큐는 유지합니다. 일회성 SYSTEM 검사, 기존 Filebeat 설정/서버 인증 검사를 통과한 뒤 누락 작업은 생성합니다. 기존 비활성 작업은 XML/해시를 보호 백업하고 실행 인자에 `-DiscoveryRoot` 및 작업 폴더를 명시한 뒤 활성화합니다. 기존 작업을 삭제/재등록하지 않고 트리거·계정·기타 설정은 유지하며 실제 작업 실행 결과도 확인합니다.
4. Filebeat를 시작하고 Running 유지 확인 후 자동 시작으로 전환합니다. 이 경로는 로그 전용 패키지용입니다. 최신 네트워크 포함 패키지는 아래의 두 서비스 통합 복구를 사용하며, Filebeat만 있는 PC에 네트워크 수집기를 자동 추가하지 않습니다.

실패하면 이번에 생성한 작업을 정리하고 원래 서비스 시작 유형 및 교체한 Discovery 파일/입력을 복원합니다. **registry/큐/keystore는 과거 백업으로 되감거나 삭제하지 않습니다.** 검사/시작 중 갱신된 큐와 진단 로그는 보존하므로 전체 파일이 과거 바이트로 돌아가는 복원은 아닙니다. 정전·강제 종료 또는 정리 실패에는 `recovery-pending.json`을 남기며 다음 실행이 무조건 덮어쓰지 않습니다. 이 경우 자동 재개는 아직 미지원입니다.

확인 메시지는 서비스/작업 복구 결과이며 **중앙 문서 수신 성공을 의미하지 않습니다.** 수신 확인 및 에이전트 등록/Enrollment, 손상된 키 교체, 서버/조직 이전, 기존 정상 설치 갱신, Packetbeat 복구는 별도 범위입니다. 실제 사용자 PC의 관리자/SYSTEM 복구 검증은 모의 테스트와 구분합니다. 기존 ZIP은 그대로이므로 포털에 코드를 배포한 뒤 새 패키지를 생성해야 합니다.

기존 작업 복구 도중 실패하면 작업을 비활성화하고 종료를 확인한 뒤 원래 실행 정의와 비활성 상태로 복원합니다. 외부에서 작업 정의를 바꾸었거나 종료되지 않으면 덮어쓰거나 파일을 되돌리지 않고 백업과 중단 기록을 보존합니다. 실행 정의의 부분 변경은 [Microsoft Set-ScheduledTask](https://learn.microsoft.com/en-us/powershell/module/scheduledtasks/set-scheduledtask)를 사용하며 작업 삭제/재등록은 하지 않습니다. `Existing Discovery task requires a different recovery path`는 이전 패키지의 제한이므로 해당 작업을 수동 삭제하는 대신 수정된 전체 패키지를 사용해야 합니다.

## 두 서비스 통합 복구

**기존 통합 복구 코드(c89f6c8)는 중앙 포털 배포와 격리 회귀를 검증했습니다. 이번 시작 직전 경합 방어와 주소 분리 보완은 아직 운영 배포 전입니다. 실제 두 서비스 통합 설치/Repair/Resume는 별도 Windows 시험 환경에서 아직 검증하지 않았습니다.** Windows 단독 네트워크 추가 설치 및 Windows·Linux 네트워크 실수신(P0C-19)은 통합 복구 검증과 다릅니다. 변경 코드를 포함한 새 Windows 로그+네트워크 패키지를 사용해야 하며, 기존 ZIP은 자동으로 바뀌지 않습니다. 웹 공개 주소와 수신 주소가 다르면 먼저 [수신 주소 분리](../deploy/server/README.md#대시보드-주소와-에이전트-수신-주소-분리)를 확인합니다.

대상은 `cloud-soc-filebeat`와 `cloud-soc-packetbeat`가 **중지된 동일 설치**입니다. 서비스가 누락된 경우에는 새 통합 설치의 보호된 최종 준비 완료 기록과 두 설치 폴더가 모두 일치해야만 복원합니다. 서버 주소·조직·CA·공식 9.5.2 배포·보호 ACL·키 저장소·개인정보 보호 코드·기존 NIC·Npcap 서비스 의존성을 검사합니다. Packetbeat는 승인된 메타데이터 전용 설정과 일치해야 합니다. Discovery는 누락되었거나 동일 설치의 유휴 native 작업이어야 하며, 실행 중/Queued 또는 구형 PowerShell 작업은 자동 변경하지 않습니다.

관리자 PowerShell에서 검증한 새 패키지 폴더를 사용합니다. 현재 정상 수집 중인 PC에서 시험을 위해 서비스를 중지하거나 이 명령을 실행하지 마세요.

```powershell
# 기존 설치의 로컬 신원만 점검: 파일/네트워크/서비스/작업 변경 없음
.\install.ps1 -Repair -DryRun

# 지원 조건을 통과한 중지 설치에서만 실행: 백업 후 두 수집기 시작에 동의
.\install.ps1 -Repair
```

승인된 사설 CA의 폐기 정보 조회 불가 옵션이 필요한 경우에만 두 번째 명령에 `-AllowUnavailableRevocation`을 추가합니다. 복구는 기존 NIC를 유지하므로 GUID를 다시 복사할 필요가 없습니다. 다른 `-InterfaceGuid`를 지정하면 이전으로 간주해 거부합니다. `-DryRun`은 SYSTEM/Npcap/인증/수신 검증이 아닙니다.

1. 두 설치와 유휴 작업의 신원을 모두 확인한 뒤 Npcap·기존 NIC·중앙 TLS를 검사합니다. 키 재입력·재발급이나 Beat 재다운로드는 하지 않습니다.
2. 기존 작업의 활성 상태와 XML을 기록하고 보호된 전체 백업 두 개의 파일 해시를 검증합니다. 위치는 `%ProgramData%\Cloud-SOC\staging\<random>\repair-backups.json`에 남습니다. 백업은 키/큐를 포함하므로 외부에 공유하지 마세요.
3. 격리 SYSTEM Discovery, 두 수집기의 설정·인증, 영구 Discovery의 신선한 보고를 모두 검증합니다. 검사 중 설정·키·코드가 바뀌면 시작하지 않고 기록을 보존합니다.
4. 검사 완료 후와 실제 시작 직전에 두 서비스의 중지/프로세스·시작 유형·Npcap 의존성·불변 파일을 다시 확인합니다. 외부에서 시작된 서비스는 채택하거나 강제로 중지하지 않으며 활성 수집기에는 입력 파일도 과거 백업으로 되돌리지 않습니다. 두 서비스를 시작하고 Running 유지 후 자동 시작으로 전환합니다. 실패하면 신원이 유지된 이번 실행의 서비스/작업 변경만 되돌립니다. **큐·registry·keystore를 백업으로 되감거나 삭제하지 않습니다.** 외부 관리자/SCM 변경과 설치기를 운영체제 수준에서 원자적으로 묶는 기능은 아니므로 유지보수 중 병행 변경은 피하세요.

새 설치기는 서비스 등록 전 `bundle-recovery.json`에 최종 설정·CA·키 저장소·코드의 해시와 설치 소유 토큰을 기록합니다. 이 기록 및 `bundle-pending.json`·최종 준비 완료 단계·두 설치 폴더가 일치하면 누락된 서비스도 두 설정/인증 검사 후에만 등록합니다. 폴더 승격 도중 중단·누락 폴더·구버전 기록·손상/변경된 설정은 자동 채택하지 않습니다. 무조건 receipt를 삭제하거나 실행 중 서비스를 재설치하지 마세요.

### 복구 자체가 중단된 경우

새 수정본은 보호된 `bundle-repair-pending.json`과 원자적으로 저장하는 `repair-state.json`으로 **명시적 재개**를 지원합니다. 두 수집기가 모두 중지되어 있고 현재 설정·키·공식 배포·작업 정의·기록된 백업 해시가 일치하는 경우에만 가능합니다. 실행 중 서비스는 재개를 위해 강제로 중지하지 않습니다.

```powershell
# 먼저 읽기 전용으로 중단 기록과 백업을 검사
.\install.ps1 -Repair -ResumeRepair -DryRun
# 지원 조건을 통과한 중지 상태에서만 새 백업과 전체 검사 후 재개
.\install.ps1 -Repair -ResumeRepair
```

사설 CA 선택 옵션이 필요한 경우 실제 재개 명령에 `-AllowUnavailableRevocation`을 추가합니다. 기존 키와 최신 큐는 유지하며 과거 백업의 큐를 복원하지 않습니다. 구형 복구 기록, 생성 성공 여부가 불명확한 서비스/작업, 활성 작업, 백업 변조, 신원 변경은 계속 차단합니다. 이 옵션은 로그 전용 패키지에는 없으며 `-UpdateDiscovery`와 함께 사용할 수 없습니다. OS 부팅 시 자동 재개 기능은 아닙니다.

완료 문구는 **로컬 복구 완료**입니다. 중앙 문서 수신은 [실제 수신 확인](installation_reference.md#설치-후-실제-로그-확인)으로 별도 검증합니다. 일반 Beat 바이너리 업그레이드·서버/조직/NIC 이전·분실 키 교체·중단 자동 재개 기능은 아닙니다.

## 남은 필수 작업

### P0C-02 종료 검증 순서

정상 수집 중인 PC를 시험용으로 중지·삭제하지 않습니다. 승인된 별도 Windows x64 VM·Npcap·NIC와 중앙 수신 경로가 있어야 아래 실제 시험을 수행할 수 있습니다. 서비스 실행/모의 시험/중앙 수신은 서로 다른 증거입니다.

| 시험 | 코드·격리 검증 | 남은 실제 검증 |
| --- | --- | --- |
| 웹/수신 주소 분리 | 기존 URL 호환·새 양 OS 번들 주소·기존 ZIP 바이트 보존 | 운영 설정 적용·새 ZIP 등록/실제 다운로드 |
| 신규 통합 설치 | 두 구성 검증 후 commit·시작 전 소유 자원 롤백 | 새 VM의 실제 ACL/SYSTEM·두 서비스 설치 및 수신 |
| 중간 실패 | 키/최신 큐 보존·외부 시작/변경 거부 | 별도 VM에서 실패 후 기존 데이터 보존·재시도 |
| 동일 설치 Repair | 보호 백업·설정/인증·작업·누락 서비스 복원 | 별도 VM의 실제 두 서비스/Discovery 복구 및 수신 |
| 중단 후 Resume | 중단 기록/백업 재검증·변조/실행 상태 거부 | 별도 VM의 실제 중단 재개 및 키/큐 보존 |
| 재부팅 | 서비스 자동 시작 설정 검사 | 정상 설치 재부팅 후 두 서비스·Discovery 및 새 수신 |

일반 Beat 바이너리 갱신과 **중단 설치의 자동 부팅 Repair**는 현재 미지원입니다. 명시적 `-ResumeRepair`나 정상 설치의 서비스 자동 시작과 혼동하지 마세요. 실제 시험 근거가 없는 행을 완료 표시하거나 무손실로 보고하지 않습니다.

- **P0C-02:** 통합 준비/commit·실패 보존·`-Repair`·확인된 누락 서비스 복원·명시적 재개는 코드/격리 시험 및 포털 배포를 검증했습니다. 양 OS 네트워크 실수신은 P0C-19에서 별도 검증했습니다. 남은 완료 시험은 새 ZIP 다운로드와 별도 Windows에서의 실제 통합 설치·Repair·중단 재개/큐·키 보존입니다. 정상 서비스의 자동 시작 설정은 설치 단계에서 적용하지만 실제 재부팅은 미검증이며 중단된 설치의 자동 부팅 Repair와 일반 Beat 업그레이드는 미지원입니다.
- **P0C-03:** 단일 사용 Enrollment 토큰과 고유 설치 테스트 이벤트 수신 확인. 만료·원자적 소비·재시도·키 발급/폐기·패키지/조직 바인딩을 함께 검증해야 합니다. Enrollment는 아직 지원하지 않습니다.
- **P0-02/03:** 기존 Windows Filebeat 복구·SYSTEM·로그 중앙 수신과 이후 양 OS 네트워크 실수신은 검증 기록이 있습니다. 두 수집기 통합 복구 시험은 모의 cmdlet·임시 파일/백업 및 패키지 검사이며 실제 통합 설치·복구를 증명하지 않습니다.

서비스 Running/TLS 확인은 **설치 단계 통과**일 뿐 전체 수집 E2E 성공이 아닙니다. 고유 이벤트 도착 확인 전에는 전체 `SUCCESS`를 표시하지 않습니다.
