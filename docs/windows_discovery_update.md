# Windows Discovery 갱신 (P2C-07)

## 적용 범위

정상 실행 중인 Filebeat의 키·설정·registry·미전송 큐는 그대로 두고, 로그 소스 탐색과 수집 통계 보고를 담당하는 native Discovery만 갱신합니다. Filebeat 버전 갱신, 서버/조직/CA 변경, 중지된 설치 복구, Packetbeat 설치·갱신은 하지 않습니다.

2026-09-28 구현된 새 옵션입니다. 기존 배포 `dc3f6b3`과 예전에 저장한 ZIP에는 이 기능이 없습니다. 코드 반영·포털 재배포 이후 **동일 서버·조직의 새 Windows 패키지를 생성**해야 합니다. 이미 발급된 ZIP은 자동 변경되지 않습니다. 실제 PC 갱신·신규 통계 수신 검증 상태는 [작업 목록](work_tracker.md)의 P2C-07을 확인하세요.

같은 날 후속 요청으로 VMware에 `p2c07-20260928` 소스 스냅샷을 배포하고 **`test-window-discovery-update-20260928-setup.zip`**을 등록했습니다. 기존 설치와 같은 설정의 이 새 패키지를 사용하세요. SHA-256은 `7f1897f536874aff6d2e0fe6f06ef67f0ada1b4532b73c4af0ef87fe968938df`입니다. 이후 사용자 PC 갱신과 중앙 수신을 확인했고, 2026-09-30에 관리자 진단 및 실제 화면 대조를 포함한 P2C-07 종료 검증을 완료했습니다. 당시 서버는 Git 커밋/푸시 없이 소스 스냅샷으로 배포했으므로 이후 Git 재빌드 전에는 실행 소스와 재빌드 대상을 확인하세요.

## 실행 순서

1. 포털에서 새 패키지를 받고 표시된 SHA-256과 ZIP 해시를 대조합니다. 기존 폴더에 덮어쓰지 않고 새 폴더에 전체 압축을 풉니다. 내부 해시 목록만으로 패키지 출처를 보증하지 않습니다.
2. 관리자 64비트 PowerShell에서 압축을 푼 폴더로 이동합니다. 기존 실행 정책은 유지합니다. 서명/조직 정책이 차단하면 승인된 배포 경로를 사용하고 정책을 우회하지 않습니다.
3. 아래 읽기 전용 점검으로 기존 서비스·서버·조직·CA·권한·native 해시를 확인합니다. 이 점검은 실제 SYSTEM 실행 성공이나 중앙 수신 성공을 뜻하지 않습니다.

```powershell
.\install.ps1 -UpdateDiscovery -DryRun
```

4. 점검 성공 후 갱신을 실행하고 확인 질문에 `y`를 입력합니다. 네트워크 포함 패키지여도 NIC 선택·Npcap 검사·Packetbeat 설치 경로는 건너뜁니다. API 키 재입력과 TLS 폐기 검사 완화 옵션은 필요하지 않습니다. 갱신기 자체는 네트워크에 접속하지 않습니다.

```powershell
.\install.ps1 -UpdateDiscovery
```

`-Repair`와 함께 사용할 수 없습니다. 일반 설치 명령을 실행해 '이미 실행 중' 안내가 나오면 서비스를 중지해서 우회하지 말고 갱신 옵션을 사용하세요.

## 보호 동작

- Microsoft 서명이 유효한 Windows .NET Framework 컴파일러로 보호 staging에서 빌드하고, 기존 설정의 사본으로 임시 SYSTEM 작업을 검사합니다. 이 단계의 입력/상태 보고는 staging에만 작성하며 수집기에 연결하지 않습니다.
- 설치/복구 간 잠금과 Discovery/정책 파일 잠금을 사용합니다. 기존 예약작업을 비활성화한 뒤 진행 중인 실행이 끝날 때까지 최대 5분 기다립니다. 기존 프로세스를 강제 종료하지 않습니다.
- `C:\ProgramData\Cloud-SOC\updates\<ID>`에 기존 소스·EXE·manifest·입력 설정·예약작업 XML과 해시 목록을 보호 백업합니다. 이는 전체 PC나 Filebeat 큐 백업이 아닙니다.
- 새 소스/EXE/manifest를 교체하고 설치 위치에서 SYSTEM 실행·최신 로컬 상태 보고·기존 키/설정과 Filebeat 프로세스 유지 여부를 확인한 다음 원래 예약 실행을 재개합니다. 계정·트리거·실행 경로를 변경하지 않습니다.
- 일반적인 교체 후 실패는 검증된 이전 프로그램·입력 설정으로 복원합니다. 전송 큐·registry·keystore·이미 생성된 상태 보고 spool은 되돌리거나 삭제하지 않습니다. 전송된 문서를 취소하는 기능이 아닙니다.
- 백업 손상, 작업 정의의 외부 변경, 끝나지 않은 임시 작업 등으로 안전한 복원을 증명할 수 없으면 보호 자료와 `discovery-update-pending.json`을 유지합니다. 강제 종료/재부팅도 자동 성공으로 취급하지 않습니다. 중단 자동 재개는 아직 지원하지 않으며 marker를 지워서 재시도하지 않습니다. Filebeat는 계속 수집할 수 있지만 Discovery 예약 실행은 중지되어 있을 수 있습니다.

갱신 중 다른 관리자가 정책 도구/설정/예약작업을 동시에 변경하지 마세요. 새 패키지의 정책 도구는 pending marker가 있으면 변경을 거부하지만, 예전에 배포한 도구에는 이 검사가 없을 수 있습니다. 외부 변경이 감지되면 원래 키/설정을 덮어쓰지 않습니다.

## 완료 확인

2026-09-28 후속 사용자 실행에서는 로컬 갱신 완료 후 중앙 품질 조회에서 새 통계의 실제 도착을 확인했습니다(15:28:39 KST 수신). 이는 해당 설치의 한 번의 운영 확인이며 다른 PC의 성공을 보장하지 않습니다. 상세 증거와 검증 범위는 P2C-07 작업 기록을 따릅니다.

2026-09-30 종료 검증에서는 지정된 보호 백업·작업의 관리자 진단 13/13 통과, 현재 Filebeat 실행 및 새 통계의 지속 수신을 확인했습니다. 실제 HTTPS 관리자 응답과 운영 화면 자산을 CA 검증 후 임시 loopback 검증 창에 표시해 시각·큐·구간 ACK 값이 일치함을 확인하고, 같은 문서의 Elasticsearch 원문과 독립 대조했습니다. 새로고침 후에도 더 최신 보고가 표시되었습니다. 원래 IP URL의 브라우저 인증서 신뢰 설정은 이번 검증에서 바꾸지 않았습니다. 직접 접속의 인증서 신뢰 문제는 별도로 해결해야 합니다. 오류 카운터는 미보고이고 읽기 범위 제한이 있어 전체 무손실 또는 오류 없음으로 해석하지 않습니다.

갱신기의 완료 메시지는 **로컬 프로그램 교체와 SYSTEM 검사**만 의미합니다. 서버 연결 장애나 전송 대기 때문에 중앙 반영은 늦을 수 있습니다.

중앙 수집 품질 화면에서 같은 수집기의 보고 생성/수신 시각이 갱신 이후인지 확인하고, 새 `collector_metrics`와 화면 값의 일치를 확인해야 운영 완료입니다. 최신 Filebeat 통계가 없으면 정상 갱신 후에도 `미측정`일 수 있습니다. 실행 중 서비스, 로컬 보고 파일, 설치기 종료 코드 0만으로 수신 완료 처리하지 않습니다.

## 개발 검증

```powershell
node --test deploy/agents/tests/update-discovery.test.cjs deploy/agents/tests/repair.test.cjs
node --test deploy/agents/tests/verify-discovery-update.test.cjs
```

위 시험은 실제 임시 파일·해시·잠금과 모의 서비스/예약작업을 사용합니다. 사용자 PC의 실제 에이전트를 갱신하지 않습니다. 실제 관리자 ACL·SYSTEM 갱신 경로와 중앙 수신은 별도 운영 검증입니다.
