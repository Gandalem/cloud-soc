# Windows / Linux 로그 수집 범위

작성일: 2026-09-21. 상태: 수집 요구사항 및 Phase A UI 확장. 실제 수집기 배포, OS 설정, 파서 또는 백엔드를 이번 작업에서 변경하지 않았다.

## 1. 목표와 전체 수집의 의미

SSH 실패나 탐지된 경보에 한정하지 않고 Windows와 Linux에서 생성되는 OS·보안·서비스·애플리케이션 로그를 통합 로그 목록에서 조회한다. 로그 종류를 추가할 수 있는 구조를 목표로 하며 아래 예시 목록을 영구적인 수집 제한으로 삼지 않는다.

전체 수집은 **등록된 호스트에서 생성되고, 승인된 접근 권한으로 읽을 수 있으며, 수집 설정에 포함된 로그를 빠짐없이 처리하는 목표**다. 미생성 이벤트, 비활성 채널, 기록 설정이 꺼진 서비스, 이미 삭제된 로그까지 복원한다는 의미는 아니다. 실제 적용 범위와 제외 사유를 소스 목록에 기록한다.

운영체제와 클라우드 플랫폼은 별도 속성이다. OCI/AWS 위에도 Windows 또는 Linux 호스트가 있을 수 있다. 클라우드 감사 API 자체에는 호스트 OS를 임의로 붙이지 않고 해당 없음으로 표시한다. 식별되지 않은 소스는 미확인으로 남긴다.

## 2. 수집 대상

아래는 설계 대상이며 모두 현재 지원 완료라는 뜻이 아니다. 경로는 예시이며 배포판, OS 버전, 설치 서비스와 로깅 설정에 따라 확인해야 한다.

| 구분 | 수집 대상 예시 | 등록 기준 |
| --- | --- | --- |
| Windows 기본 이벤트 | Security, System, Application, Setup, ForwardedEvents | 실제 존재하는 이벤트 채널과 읽기 권한 |
| Windows 운영/보안 이벤트 | PowerShell, Defender, Sysmon, TaskScheduler 등 | 설치·활성 상태, 채널의 정확한 이름, 기록 정책 |
| Windows 역할/서비스 | IIS, DNS, 방화벽, 데이터베이스 등 | 서비스별 이벤트 채널 또는 파일 경로/형식 |
| Windows 사용자 지정 | 프로그램별 텍스트·JSON·다중 행 파일 및 사용자 지정 이벤트 채널 | 소스별 등록과 파서/인코딩 설정 |
| Linux 인증/권한 | SSH, sudo, PAM, auth.log 또는 secure 등 | 실제 출력 경로 또는 저널, 읽기 권한 |
| Linux 시스템 | syslog/messages, journald, kernel, cron 등 | 배포판·서비스별 출력과 중복 여부 |
| Linux 감사/네트워크 | auditd, 방화벽 등의 기록 | 로깅/감사 정책이 실제로 생성하는 이벤트 |
| Linux 서비스 | 웹 서버, DB, 컨테이너, 사용자 애플리케이션 | 파일·저널·표준 출력 전달 경로 등 소스별 입력 |
| Linux 특수 형식 | 바이너리 회계/로그인 기록 등 | 텍스트 파일 수집과 분리된 전용 디코더 검토 |

Windows 이벤트 수집은 개별 채널을 지정하는 방식을 기준으로 검토한다. 전체 이름과 누락/접근 실패 처리를 정해야 하며, 특정 채널이 없는 호스트를 정상 수집 완료로 간주하지 않는다. [Elastic Winlogbeat 설정 문서](https://www.elastic.co/docs/reference/beats/winlogbeat/configuration-winlogbeat-options)

Sysmon은 해당 호스트의 설치 또는 기능 활성화와 기록 설정을 확인한 뒤 대상으로 등록한다. OS 버전별 제공 방식을 동일하다고 가정하지 않는다. [Microsoft Sysmon 활성화 문서](https://learn.microsoft.com/en-us/windows/security/operating-system-security/sysmon/how-to-enable-sysmon)

Linux 저널은 단순한 텍스트 경로 와일드카드와 구분하여 journald 입력을 검토한다. 커서와 재시작 동작, 실행 환경 의존성을 확인해야 한다. [Elastic Filebeat journald 입력 문서](https://www.elastic.co/docs/reference/beats/filebeat/filebeat-input-journald)

## 3. 향후 구현 계약

계획 흐름: 소스 등록 → OS별 수집 입력 → 원문 저장 → 파서 선택/필드 정규화 → 통합 조회. 탐지는 후속 소비자이며 탐지 여부로 로그 목록을 제한하지 않는다.

- 소스 등록: 호스트 식별자, OS, 환경, 플랫폼, 채널/파일/저널, 입력 유형, 활성 여부, 승인/제외 사유, 읽기 권한, 파서와 보존 정책을 기록한다.
- 수집 입력: Windows 이벤트용 입력과 파일용 입력, Linux 파일·저널 입력을 구분한다. 기존 Filebeat 설정 하나가 Windows 이벤트나 모든 특수 형식을 자동 지원한다고 가정하지 않는다. 제품/버전 선택과 실제 구성은 별도 단계다.
- 전달 신뢰성: 재시작 시 커서/오프셋, 파일 회전, 재전송/중복, 과거 로그 시작점, 큐 포화와 유실 관측을 검증한다. 파일과 저널에 같은 이벤트가 기록되는 경우 중복 수집 기준을 정한다.
- 원문 보존: 수집된 원문 참조와 소스 메타데이터를 유지한다. 알 수 없는 형식이나 파싱 실패도 버리지 않고 목록과 실패 이유를 남긴다. 보존·마스킹·접근 정책을 함께 적용한다.
- 정규화: 이벤트 시각과 수집 시각을 분리한다. IP/사용자/결과가 없는 소스에는 값을 만들지 않는다. OS별 필드, 채널/프로바이더/이벤트 코드 또는 파일 출처는 관측된 경우에만 추가한다.
- 파서 확장: 알려진 소스별 파서를 등록하고 미지원 형식은 원문으로 수집한다. 수집 가능과 자동 필드 해석 가능을 별도 지원 상태로 관리한다.
- 상태 표현: 등록 소스별 정상/미설정/미지원/권한 오류/지연/파싱 실패를 분리한다. 수집 0건만으로 정상 또는 공격 없음이라고 판정하지 않는다.
- 보안과 비용: 전체 디스크나 모든 파일을 무차별 수집하지 않는다. 비밀키·토큰 등 민감정보의 제외/마스킹, 최소 권한, 암호화 전송, 조회 권한, 보존 기간, 일별 용량을 설계한다. 감사 정책이나 접근 권한 확대는 별도로 승인받는다.

수용 기준은 OS별 등록 소스에서 알려진 테스트 이벤트 생성 후 **원문 저장 → 필드 확인 → 통합 목록 → 원문 재조회**가 같은 참조로 연결되는 것이다. 파싱 실패, 접근 거부, 수집 중단, 파일 회전, 재시작 및 중복 시나리오도 검증한다. 현재 정적 UI는 이 실제 수용 기준을 충족한 것으로 판정하지 않는다.

## 4. 현재 UI 반영

- `prototype/logs.html`에 운영체제 필터, 수집 대상 설명, 운영체제와 채널/파일/저널 컬럼을 추가했다.
- OS는 Windows/Linux/해당 없음(클라우드 API)/미확인으로 구분한다. 기존 환경·플랫폼·로그 소스 등과 AND로 결합한다.
- 수집 정보 상세에는 운영체제와 출처를 표시한다. 파싱 필드의 `host.os.type`, `winlog.channel`, `log.file.path`는 합성 예시다. Windows 원문 예시도 실제 Event XML/Winlogbeat 출력이 아닌 `prototype: true` JSON이다.
- 90건: Windows 24건, Linux 54건, 클라우드 API 6건, 미확인 6건. 파싱 완료 78건, 일부 누락 6건, 실패 6건이다. 일반 OS 활동의 결과는 미확인으로 유지하며 성공을 임의로 만들지 않는다.
- UI에 적힌 넓은 수집 대상 전체가 fixture로 재현된 것은 아니다. 미구현 소스 등록·건강도 기능을 숫자나 성공 배지로 가장하지 않는다.

검증 명령: `node --test prototype/tests/logs.test.cjs`. 실제 OS 로그 읽기, 수집 설정 적용, Elasticsearch 조회 및 백엔드 연결은 수행하지 않는다.

## 5. 클라우드 API 감사 로그와의 구분

OS 로그 수집 범위를 넓혀도 클라우드 서비스의 API 감사 로그를 대체하지는 않는다. AWS CloudTrail과 OCI Audit은 호스트 OS와 별도 소스로 설계한다. 사용자가 제공한 AWS S3 공격 재현 데이터의 확인 결과와 향후 파싱/조사 제안은 [Security Datasets 참고 검토](reference_securitydatasets_aws_s3.md)에 기록했다. 이번에는 참고 문서만 추가하며 실제 AWS 수집 지원이나 파서 구현을 선언하지 않는다.
