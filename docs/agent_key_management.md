# 에이전트 발급 키 관리

## 삭제와 폐기의 차이

- **설치 파일 목록의 패키지 삭제:** 다운로드 파일과 링크만 삭제합니다. 설치된 에이전트와 발급 키는 중지하지 않습니다. 발급 후에도 패키지 삭제는 가능합니다.
- **발급 키 관리의 키 폐기 (사용 중지):** 키를 사용하는 수집기의 전송을 중지합니다. 대상·용도·키 ID를 확인한 뒤 `확인 후 키 폐기`를 선택하세요. 로그 키와 네트워크 키는 별개입니다.
- **발급 이력:** 폐기 후에도 감사용으로 남깁니다. 목록을 정리하려면 상태 필터에서 `폐기 완료 제외`를 선택하세요. 이력 영구 삭제 기능은 제공하지 않습니다.

폐기는 Elasticsearch가 해당 ID를 폐기했거나 이미 폐기한 것으로 응답해야 성공 처리합니다. 빈 응답·다른 ID·오류는 성공이 아닙니다. 실패 시 화면 안에 오류가 남으며 재시도할 수 있습니다. 원격 폐기 후 포털 저장에 실패한 경우에도 같은 키로 재시도하세요. 키가 서버에서 자동 정리되어 더 이상 조회되지 않으면 임의로 폐기 완료라고 표시하지 않습니다.

Elasticsearch도 키 무효화와 이력의 즉시 삭제를 구분합니다. [공식 키 무효화 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-security-invalidate-api-key)를 참고하세요.

## 키 식별

발급 시 선택한 패키지와 함께 **대상 별칭**을 입력할 수 있습니다. 예: `VMware Windows 실습 01`. 키 원문이나 비밀번호를 별칭에 입력하지 마세요.

목록에는 Filebeat 로그 / Packetbeat 네트워크 용도, 패키지 이름, OS, 조직, 직접 입력한 대상 별칭, 발급·만료·서버 조회·폐기 확인 시각이 표시됩니다. 별칭은 나중에도 수정할 수 있습니다. 저장 실패 시 입력 초안을 유지합니다. 별칭·패키지·조직·용도·ID로 최근 500개 내에서 검색합니다.

**별칭은 실제 설치 호스트와의 자동 매칭이 아닙니다.** 키 유효 상태도 에이전트 설치나 실제 로그 수신을 증명하지 않습니다. [에이전트 수신 현황](agent_status.md)을 별도로 확인하세요. 키 원문은 발급 응답에서 한 번만 표시하며 DB와 목록에 저장하지 않습니다.

## 상태와 기존 키

- `서버 확인 전`: 발급 이력만 있으며 서버의 현재 상태를 조회하지 않았습니다.
- `유효 (마지막 확인 기준)`: `서버 확인`을 누른 시점에 유효했습니다. 실시간 자동 동기화가 아닙니다.
- `만료`: 기록된 만료 시각을 지났습니다.
- `폐기 완료`: 폐기 응답 또는 서버 조회에서 무효화가 확인됐습니다. 다시 열어도 유지합니다.
- `서버 확인 실패` / `서버에서 찾지 못함`: 연결·발급 계정 권한·클러스터 변경·서버의 오래된 키 정리 등을 확인해야 합니다. 정상이나 폐기 성공으로 간주하지 않습니다.

구버전 DB는 키 ID·패키지 ID·발급 시각만 저장했습니다. 새 버전은 기존 이력을 보존하면서 열을 추가하고, 패키지가 남아 있으면 이름·OS·조직을 보완합니다. 용도와 만료는 추측하지 않습니다. 각 키의 `서버 확인`은 등록된 정확한 키 ID와 발급 계정 소유 범위로만 조회합니다. 패키지 ID가 일치하고 역할이 식별되는 키만 용도를 보완합니다. [공식 키 정보 조회 API](https://www.elastic.co/docs/api/doc/elasticsearch/operation/operation-security-get-api-key).

이미 삭제된 패키지의 이름이나 과거에 기록하지 않은 실제 설치 대상은 자동 복구할 수 없습니다. 대상 별칭을 직접 기록하세요. 포털을 거치지 않고 발급한 키는 목록에 추가하지 않습니다.

## 기존 VM 적용

이 문서는 코드 변경 안내이며 VMware 서버에 원격 배포한 기록이 아닙니다.

1. 변경 코드가 Git에 반영된 후 기존 중앙 서버에서 코드를 업데이트합니다. 로컬 변경이 있으면 먼저 보존·검토합니다.
2. 새 버전의 [포털 백업 도구](portal_backup.md)로 기존 DB를 백업하고 검증합니다. 도구는 구버전·신버전 키 이력 형식을 모두 읽습니다.
3. 포털 이미지를 재빌드하고 포털만 재생성합니다. 기존 `state`나 Elasticsearch 볼륨을 삭제하거나 신규 설치기를 다시 실행하지 않습니다.
4. 브라우저를 새로고침한 뒤 `발급 키 관리`에서 기존 키 하나를 `서버 확인`합니다. 에이전트 재설치나 새 키 발급은 필요하지 않습니다.

```bash
sudo docker compose --env-file state/server/compose.env -f deploy/server/compose.yaml build portal
sudo docker compose --env-file state/server/compose.env -f deploy/server/compose.yaml up -d --no-deps portal
```

이 변경을 위해 발급 계정 권한을 넓히지 않습니다. 새 DB를 구버전 포털에 바로 연결하는 다운그레이드는 지원하지 않습니다. 롤백 시 앱/DB 버전을 함께 검토하고, DB 복원으로 Elasticsearch의 폐기된 키가 되살아나는 것은 아니라는 점에 유의하세요.

## 검증 범위

`tests/test_key_management.py`는 가짜 발급 서버와 임시 DB로 정보 보존·구버전 이행·확인/폐기 응답·권한/CSRF·백업 복원을 검증합니다. `prototype/tests/key-management.test.cjs`는 검색·필터·확인/취소·오류·초안·패키지 삭제 재시도를 검증합니다. `tests/key_management_preview.py`는 임시 상태와 합성 인증만 사용하는 루프백 화면 검증용이며 운영 실행기가 아닙니다. 실제 VMware ES 권한/연결 및 에이전트 전송 중지 확인은 별도입니다.
