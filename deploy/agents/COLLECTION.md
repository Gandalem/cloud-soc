# 자동 수집 계약

## 무엇을 모두 수집하는가

사용자가 로그 이름을 하나씩 나열하지 않아도 **지원하는 시스템 로그 저장소와 로그 디렉터리에서 읽을 수 있는 소스를 발견**합니다. 탐색 단계에서 이벤트 ID·심각도·성공/실패로 필터링하지 않습니다. 이후 개인정보 보호 정책으로 본문/필드 또는 레코드가 제외될 수 있습니다. 이것은 모든 디스크 파일이나 생성되지 않은 기록까지 수집한다는 뜻이 아닙니다.

P3의 privacy v2에서는 Windows 렌더링 메시지·명령줄·작업 XML/스크립트 본문 및 네이티브 Linux Audit 인자 레코드(EXECVE/PROCTITLE/USER_CMD)를 제외합니다. 메타데이터 해석 범위와 감사 설정 사전 조건은 [호스트 감사 가이드](../../docs/host_security_audit.md)를 확인하세요. Sysmon/auditd·감사 정책·SACL은 자동 설치/변경하지 않습니다.

| 범위 | 구현 |
| --- | --- |
| Linux 시스템 journal | journald 입력이 기본 journal 전체를 읽고 커서를 저장. 최초 실행은 보존 중인 기록의 처음부터 시작 |
| Linux 텍스트 로그 | `/var/log`와 추가 로그 루트를 깊이 제한 없이 재귀 탐색. 빈 파일은 다음 탐색에서 다시 검사 |
| Windows 이벤트 | 설치된 모든 활성 지원 채널 자동 등록. 이벤트 ID·level·provider 필터 없음 |
| Windows 파일 | 표준 로그 루트와 추가 앱 로그 루트의 텍스트 파일 재귀 탐색. IIS 파일도 해당 경로에 있으면 포함 |
| 새 소스 | 설치 시 발견 목록을 만들고, 1분마다 재탐색. Filebeat는 변경된 외부 입력을 10초마다 확인 |

파일 경로 목록을 직접 발견하므로 Filebeat의 `**` glob 깊이 제한에 의존하지 않습니다. root와 input ID는 재실행에도 동일하게 유지합니다. 입력의 파일 목록 변경 시 Filebeat가 입력을 재시작할 수 있으며 registry는 유지합니다.

## 제외와 제한

- 비활성 채널과 꺼진 감사 정책은 자동으로 활성화하지 않습니다. 기록이 생성되지 않으면 수집할 수 없습니다.
- Windows Analytic/Debug 직접 채널은 구독 방식으로 읽을 수 없어 `unsupported_direct_channel`로 보고합니다. 별도 ETW 설계가 필요합니다. [Microsoft EvtSubscribe 제한](https://learn.microsoft.com/en-us/windows/win32/api/winevt/nf-winevt-evtsubscribe).
- Linux 파일은 `file --mime-encoding`이 ASCII/UTF-8로 판단한 파일을 대상으로 합니다. Windows는 최대 8KB 표본으로 UTF-8과 BOM이 있는 UTF-16LE/BE를 판별합니다. 이는 형식의 완전한 증명이 아니며 혼합 인코딩이나 나중에 바이너리로 바뀐 파일은 별도 확인이 필요합니다.
- 압축 파일, 바이너리 journal/EVTX/ETL, DB·메모리 덤프, 알려진 키·인증서 파일은 텍스트 입력으로 읽지 않습니다. journal과 활성 이벤트 채널은 각각 전용 입력에서 처리합니다. 삭제된 로그나 아카이브의 전체 복원 기능은 없습니다.
- 심볼릭 링크·Windows reparse point는 따라가지 않습니다. 권한 없는 소스, 안전하게 표현할 수 없는 경로도 보고하고 제외합니다. 탐색과 읽기 사이 파일 교체까지 방어하는 보안 격리 기능은 아닙니다.
- 기본 로그 디렉터리 밖의 앱 로그는 `--log-root` 또는 `-AdditionalLogRoot`로 디렉터리를 추가해야 합니다. 홈 디렉터리·문서·전체 드라이브를 무차별 탐색하지 않습니다. 클라우드 Audit API와 원격 저장소·컨테이너 전용 로그 드라이버는 별도 연동이 필요합니다.
- 텍스트 로그는 기본적으로 줄 단위 수집입니다. 멀티라인 스택 트레이스 결합, 서비스별 파싱·정규화·탐지는 별도 구현입니다. 매우 긴 레코드와 마지막 개행 없는 파일은 Filebeat 입력 제한에 대한 검증이 필요합니다.

## 중복과 저장량

journald 이벤트를 rsyslog가 파일에도 기록하면 journal과 파일 양쪽에 같은 활동이 존재할 수 있습니다. 두 소스 모두 보존하며 `labels.log_source`로 구분합니다. 의미상 중복을 제거하지 않습니다. 파일 회전·단절·복구도 중복/유실 검증이 필요합니다.

최초 시작부터 과거 보존 로그가 유입될 수 있고, raw에 개인정보·토큰 등 민감정보가 포함될 수 있습니다. 저장소 접근 권한·보존 기간·전송량·용량을 먼저 정해야 합니다. 자동 수집 확대가 마스킹이나 접근 통제를 대신하지 않습니다.

Filebeat 자체 로그를 다시 수집하는 루프를 피하기 위해 수집기 로그는 보호된 에이전트 폴더 안에 기록하고 Linux의 자체 서비스 journal은 제외합니다. 기본 디스크 큐 1GB는 무손실 전송을 보장하지 않습니다.

## 보고서 해석

설치 경로의 `discovery-report.json`은 최근 성공한 탐색 시각과 소스별 상태를 제공합니다.

| 상태 | 의미 |
| --- | --- |
| `selected` | 입력 설정에 포함. 실제 전송 여부는 Filebeat와 Elasticsearch에서 확인 |
| `empty_pending` | 아직 내용이 없어 다음 탐색에서 재검사 |
| `disabled` | 비활성 Windows 채널 |
| `unsupported_direct_channel` | Windows Analytic/Debug 채널 |
| `binary_archive_or_secret` | 알려진 바이너리·압축·키 형식 |
| `binary`, `unsupported_encoding`, `unsupported_encoding_or_binary` | 텍스트 판별 또는 지원 인코딩 조건 미충족 |
| `symlink`, `reparse_point`, `unsafe_path`, `unsafe_name` | 따라가지 않는 링크 또는 지원하지 않는 이름 |
| `unreadable`, `enumeration_error`, `missing` | 접근 실패, 채널 목록 조회 실패, 없는 디렉터리 |

보고서에 없는 위치까지 확인했다는 의미는 아닙니다. Linux 보고서는 파일 목록이며 journal 접근 오류는 Filebeat 로그에서 확인합니다. Windows 채널의 실제 읽기 권한은 입력 시작 시에도 실패할 수 있습니다.

탐색 전체 실패 시 설정을 유지하므로 **보고서 시각이 오래되었다면 정상으로 간주하면 안 됩니다.** timer/service 또는 예약 작업 종료 코드와 에이전트 로그를 함께 확인하세요. 일시적으로 읽을 수 없는 개별 파일은 다음 탐색에서 다시 시도합니다. 탐색 주기 사이에 생성·삭제되는 짧은 수명의 파일까지 보장하지는 않습니다.

## 기존 설치 전환

P2 추가: 새 설치에는 전송 전 보호 처리와 별도 `soc-agent-health-*` 보고가 포함됩니다. 정책 v1 지원 설치에서는 로컬 `policy.py`로 승인 경로/제외 목록을 갱신할 수 있습니다. 구버전의 전체 자동 업그레이드와는 다릅니다. 상세 범위와 제한은 [수집 보호·품질 가이드](../../docs/collection_protection.md)를 참고하세요.

현재 도구는 신규 설치 전용입니다. 기존 설치에 실행하면 중단하며 자동 교체하지 않습니다. Windows는 Winlogbeat에서 Filebeat로 바뀌므로 기존 registry를 그냥 복사해서 이어 읽을 수 있다고 가정하지 않습니다.

전환 전 기존 설정·registry·미전송 큐를 보존하고, 별도 테스트 서버에서 검증한 뒤 수집기 중복 실행 없이 전환해야 합니다. 신규 입력 ID로 과거 기록이 다시 유입될 수 있으므로 재수집 범위와 중복 처리 방침을 먼저 정합니다. 데이터 디렉터리를 삭제해서 충돌을 해결하지 않습니다.

중앙 Elasticsearch 인덱스와 Python SSH 파이프라인은 변경하지 않았습니다. 자동 수집 후 분석까지 자동 지원되는 것은 아닙니다.
